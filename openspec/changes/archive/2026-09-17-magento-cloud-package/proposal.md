# Proposal: magento-cloud-package — `hiberus-magento-cloud` CLI and `hiberus-magento-cloud-mcp` server

## Intent

Three packages in, `mcp-core`'s allowlisted command executor has never executed anything but `/bin/echo`, `/bin/true` and `/bin/sleep` in its own tests. `eds` and `aco` are pure HTTPS clients. This change is the first package that actually shells out, and it is the package the founding brief designed the executor for: the brief's own `mcp-core` example is `runAllowed({ bin: "magento-cloud", subcommand: "environment:list", ... })`, and its own `servers.json` example declares `requires: { binaries: ["magento-cloud"] }`.

**This package wraps the real `magento-cloud` CLI.** It does not call Magento Cloud REST endpoints directly. The audited third-party fork went REST-direct and an earlier exploration pass drifted with it, because it was reading the fork instead of the brief. Wrapping the CLI resolves every objection at once: we never invoke `ssh` ourselves (the CLI does that internally, which is its business), authentication is the CLI's job once it holds a token, and the executor finally gets a real consumer.

Being that first consumer surfaced one genuine gap, which this change also fixes.

## Scope

### In Scope

**`packages/magento-cloud`**, scaffolded from `templates/server/` via `pnpm new-server`, with the architecture `eds` and `aco` established (`client/` boundary, `client/index.ts` the sole public surface, thin `cli.ts`/`mcp.ts` adapters, no `console.*`/`process.exit`/`process.env`/prompts/colour inside `client/`):

- An **explicit allowlist of read-only subcommands** registered on `CommandAllowlist`, argv builders per subcommand, and a TSV response parser.
- A **hardened `db:sql`** guard: single-statement `SELECT`/`SHOW`/`DESCRIBE`/`EXPLAIN` only, no `SELECT *`, no `INTO OUTFILE`/`INTO DUMPFILE`/`LOAD_FILE(`, a mandatory injected `LIMIT`, and `maxOutputBytes` as an independent second cap.
- Explicit child-environment assembly (`MAGENTO_CLOUD_CLI_TOKEN`, `HOME`, `PATH` — named, never inherited wholesale), resolved through `mcp-core`'s existing `resolveCredentialValue`/`MissingCredentialError`.
- Eight task-shaped MCP tools, a `hiberus-magento-cloud` CLI, a `servers.json` entry, the README regenerated by the existing generator, and a Strict-TDD suite over synthetic fixtures.

**`packages/mcp-core`** — one additive, optional `CommandSpec.env` field (see Approach). The first `mcp-core` change in four changes; surgical and additive by construction.

**`packages/mcp-testing`** — additive synthetic constants for project/environment identifiers in `synthetic-identifiers.ts`. No requirement changes.

### Out of Scope

- **Any REST call to Magento Cloud.** Every operation goes through the CLI binary.
- **Every mutating subcommand**, never registered at all: `ssh`, `environment:ssh`, `environment:scp`, `environment:drush`, all five `tunnel:*` forms, `db:dump`, `snapshot:*`, `mount:*`, `local:*`, `server:*`, `self:*`, `operation:run`, `console`, every mutating `environment:*`/`user:*`/`team:*`/`organization:*`/`integration:*`/`resources:*`, and the CLI's own generic REST passthroughs `api:curl`/`project:curl`/`organization:curl`/`environment:curl` — an arbitrary REST passthrough is the same shape the brief bans a raw `ssh` tool for.
- **Moving forbidden-command knowledge into `mcp-core`.** `FORBIDDEN_TOKENS` stays exactly as it is. A domain-agnostic library cannot know what `tunnel` means in every domain; this package knows its own CLI's surface, so the exclusion lives here as an allowlist plus a test.
- **A real SQL parser** for `db:sql` (see Risks — residual gap stated, decision deferred to design).
- Interactive login from the server. The CLI logs in; the MCP server only reads.
- Raw `environment:relationships` output on the MCP surface — it carries live service credentials. CLI-only.
- Dockergento (change 5).

## Capabilities

### New Capabilities

- `magento-cloud-client`: the domain layer — the read-only subcommand allowlist and its argv builders, the TSV parser, the `db:sql` guard (statement kind, `SELECT *`, file-exfiltration forms, `LIMIT` injection and row-cap rejection), explicit child-environment assembly, CLI-failure classification (not-installed / not-authenticated / unsupported-version / timeout-vs-output-cap), and the `client/` purity constraints.
- `magento-cloud-cli`: the `hiberus-magento-cloud` binary — command surface, token intake and `auth status`, raw relationships output, and the CLI-only operations excluded from MCP.
- `magento-cloud-mcp`: the `hiberus-magento-cloud-mcp` server — the eight-tool task-shaped surface, its annotations, the never-optional `db:sql` query argument, and the registered-command-key assertion.

### Modified Capabilities

- `mcp-core`: "Allowlisted Command Executor" gains an optional, explicit per-spec child environment. The requirement that the executor MUST NOT inherit `process.env` wholesale is strengthened, not weakened — it becomes an assertable property rather than an incidental consequence of a hardcoded `{}`.

`mcp-conformance` is **not** modified. Its `shellOutProbe` and `readOnlyIntrospections` options already exist and are already specified as optional; this change is their first real caller, not a requirement change.

## Approach

### The `mcp-core` change: one optional field, and why it is allowed here

`run-allowlisted.ts` hardcodes `env: {}` under a comment promising "an explicit, minimal environment", while `CommandSpec` provides no way to supply one. Node's `env` option **replaces** rather than merges, so a spawned `magento-cloud` gets no `MAGENTO_CLOUD_CLI_TOKEN` (cannot authenticate), no `HOME` (cannot find its own config directory) and no `PATH`. No authenticated external CLI can work at all. Three changes of unit tests missed it because they only ever ran binaries that need zero environment.

```ts
readonly env?: Readonly<Record<string, string>>;   // CommandSpec, optional
```

merged explicitly at the spawn site (`env: { ...spec.env }`), absent meaning `{}` exactly as today. **`process.env` is never spread in.** That safety property is the whole point and a test must prove it: a sentinel variable set in the parent process must be invisible to the child.

Why this change is allowed where the `FORBIDDEN_TOKENS` change was refused: *which* variables to pass is domain knowledge and stays in the domain package; *that* an explicit environment can be passed at all is a structural capability every future exec-based package needs. The values are selected by name in `packages/magento-cloud`, never in `mcp-core`.

The allowlist is constructed at server start, after the credential resolves, so a static per-spec field is sufficient; a rotated token means a restart, which is stated rather than engineered around.

### TSV, because there is no JSON

The CLI is Adobe's white-label of the Platform.sh CLI, and **it has no JSON output format**: `--format` accepts exactly `table|csv|tsv|plain` and throws on anything else. This is a constraint of the tool, not a choice we are making. `tsv` is safe to parse — it is produced by a real CSV formatter that quotes and escapes embedded tabs and newlines, and selecting a machine-readable format also suppresses the CLI's human narration banners. Every list-shaped subcommand is invoked with `--format=tsv` and parsed by one internal header-plus-rows parser.

### `db:sql`: diagnose without draining

The fork's validator permitted `SELECT * FROM <table>` unbounded — the exact full-table exfiltration the brief bans `db:dump` for, reachable one table at a time. The guard here, in order:

1. Reject anything but a single statement whose leading verb is `SELECT`/`SHOW`/`DESCRIBE`/`DESC`/`EXPLAIN`; reject any additional top-level `;`-separated statement.
2. Reject `SELECT *` and `SELECT DISTINCT *`.
3. Reject `INTO OUTFILE`, `INTO DUMPFILE` and `LOAD_FILE(`.
4. For `SELECT` only: an existing trailing `LIMIT` above the row cap is **rejected**, not clamped — clamping hides a caller's wrong assumption. An absent `LIMIT` is appended before the text ever reaches `buildArgv`.
5. `--raw` for batch, tab-separated output, plus `maxOutputBytes` as an independent second cap.

The injected `LIMIT` bounds rows at the SQL engine before output exists; `maxOutputBytes` bounds bytes after. Two independent limits, neither substituting for the other.

**The schema makes `query` mandatory.** At the CLI level it is optional, and omitting it opens an interactive remote SQL console with a requested TTY — a hang inside an MCP server, which the programme forbids. That shape must be unconstructible.

Local injection is structurally impossible regardless of query content: `execFile` passes the query as one argv element with `shell: false`. The SSH-hop shell boundary is escaped by the CLI itself, not by us.

### Telling a timeout apart from an output cap

`CommandResult.timedOut` is `error.killed && error.signal === "SIGKILL"`, and Node's `execFile` uses the same kill signal for a `maxBuffer` overflow as for a timeout. For `db:sql` the difference matters: hitting the byte cap is a normal, explainable outcome; a timeout is not.

The domain wrapper disambiguates in-domain, with no further `mcp-core` change: it measures elapsed wall-clock around the call and compares captured output length against `maxOutputBytes`. Output at the cap with elapsed well under `timeoutMs` is classified `output-cap-exceeded`; elapsed at or beyond `timeoutMs` with output below the cap is `timed-out`. When both hold, the error names both causes and both remedies rather than asserting one wrong cause.

### MCP surface: eight thick, task-shaped tools

| Tool | Arguments | Wraps | `readOnly`/`destructive`/`idempotent` |
|---|---|---|---|
| `magentocloud_auth_status` | `{}` | `auth:info --no-auto-login` | `true / false / true` |
| `magentocloud_list_projects` | `{ region?, page?, count? }` | `project:list` | `true / false / true` |
| `magentocloud_describe_project` | `{ projectId }` | `project:info` + `subscription:info` | `true / false / true` |
| `magentocloud_list_environments` | `{ projectId, status?, type? }` | `environment:list` | `true / false / true` |
| `magentocloud_describe_environment` | `{ projectId, environmentId }` | `environment:info` + `environment:url` + `route:list` | `true / false / true` |
| `magentocloud_get_environment_config` | `{ projectId, environmentId, include: ("variables"\|"appConfig"\|"services"\|"serviceEndpoints")[] }` | `variable:list`/`variable:get`, `app:config-get`, `service:list`, `environment:relationships` | `true / false / true` |
| `magentocloud_get_activities` | `{ projectId, environmentId?, activityId?, limit? }` | `activity:list` + `activity:log`/`activity:get` | `true / false / true` |
| `magentocloud_query_database` | `{ projectId, environmentId, request: { kind: "size" } \| { kind: "select", query, maxRows? } }` | `db:size` / `db:sql --raw` | `true / false / true` |

Eight, not nine or six, because that is what the evidence supports: each one answers a question an operator actually asks, and no subcommand in the allowlist is left stranded.

`magentocloud_query_database` takes a **discriminated shape, not a boolean** — there is no `includeSize` flag and no free-form mode string. `serviceEndpoints` returns host/port/scheme/service only; username and password are stripped at the client boundary before the value ever reaches a tool result, and `mcp-core`'s secret redaction runs over the rest. The unstripped payload stays CLI-only, where a human is present. `variable:list` values marked sensitive are already blanked by the CLI itself — a real, independent safety net we inherit rather than build.

### Failing fast when the CLI is missing, unauthenticated, or wrong

`runAllowlisted` always uses `stdio: "pipe"`, so the spawned CLI never has a controlling TTY, so its own interactive-login branch is structurally unreachable: it falls straight through to an error naming `MAGENTO_CLOUD_CLI_TOKEN`. That guarantee falls out of the existing architecture for free once the env gap is closed. A missing binary (`ENOENT`) and an unsupported version are classified separately, each with its own remedy. `servers.json` declares `"magento-cloud"` in `requires.binaries` alongside the package's own bin — new precedent in the manifest's *data*, not its *shape*; `binaries` is already a bare `string[]`.

### Testing without a real CLI or a real project

CI must never need a `magento-cloud` installation, an account, or network access. Two tiers, framed here and settled in design: (1) unit tests that mock `node:child_process` entirely and assert exact `argv` **and** the exact env map — this covers `LIMIT` injection, the `SELECT *` rejection, forbidden-subcommand registration and env assembly with zero real dependency; (2) a small number of real-process tests against a checked-in, executable fake `magento-cloud` script that emits canned TSV and canned error output for known argv shapes, mirroring `mcp-core`'s own use of real trivial binaries.

### First real exercise of the conformance suite's exec path

`shellOutProbe` and `readOnlyIntrospections` were added in change 2 for a pure-HTTPS package's sake and have never had a real caller — `eds` and `aco` both pass no `shellOutProbe`. This package supplies both: the probe against a genuine `execFile`-based read-only tool (proving fd-1 isolation holds for a real child process, not the synthetic `read-echo` fixture), and `readOnlyIntrospections` against `CommandAllowlist.listCommandKeys()`'s real output. They must be proven to work here, not assumed to.

### Written from scratch

The audited MIT fork is a behavioural reference for which capabilities matter. It is never a source to copy. No line of it is carried over.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| **The env gap is load-bearing — until it is fixed no tool can authenticate at all** | High (certain) | Sequenced first, before any tool work. The `mcp-core` field, its merge, and its non-inheritance test land as work unit 1; every later unit depends on it. A package built on top of an unfixed executor would fail only at the very end, against a real binary. |
| **`CommandResult.timedOut` cannot distinguish a timeout from a `maxOutputBytes` overflow** — same `killSignal` for both | High (certain) | In-domain disambiguation by elapsed time versus captured output length (see Approach); when genuinely ambiguous the error names both causes and both remedies. No `mcp-core` change; `timedOut` keeps its current meaning for existing callers. |
| **The `SELECT *` check is regex-based and a qualified `t.*` can slip it** | Medium | **Stated, not solved.** A real SQL parser would close it and conflicts with the `dependencies: {}` single-file-bundle constraint; the trade is a design decision, not a proposal one. Residual exposure is bounded by two independent caps that do not depend on the regex: the injected `LIMIT` and `maxOutputBytes`. Design must either close it or record the acceptance explicitly. |
| **Testing without a real CLI, account or network** | High (certain) | Two tiers — mocked `child_process` unit tests asserting exact argv and env, plus a checked-in fake binary for real-process coverage. CI never installs `magento-cloud` and never holds a credential. |
| **`shellOutProbe` and the contaminating-exec control have never had a real caller** — both added for a pure-HTTPS package's sake | Medium | This package supplies both and must prove them; if either fails against a real child process, that is a genuine finding about change 2's mechanism, surfaced here rather than assumed away. |
| **Third-party binary dependency: missing, unauthenticated, or wrong version** | High | `requires.binaries` declares `"magento-cloud"`. `ENOENT`, not-authenticated and unsupported-version are three distinct classified failures, each with its own remedy. The `stdio: "pipe"` guarantee means the CLI can never hang on a prompt. |
| **`environment:relationships` returns live service credentials** | Medium | Username and password stripped at the client boundary before any tool result is built; `mcp-core` secret redaction over the remainder; the unstripped payload is CLI-only. A test asserts no credential-shaped field survives into the tool result. |
| **A forbidden subcommand registered by mistake** — `mcp-core`'s exact-token check does not catch `tunnel:open`/`tunnel:close`/`tunnel:info` | Low | Not a hole: the executor is allowlist-based, so nothing exists unless deliberately registered. Defended in-domain by an explicit allowlist plus a test asserting `ssh`, every `tunnel:*` form and `db:dump` are never among the registered command keys. |
| **Real project/environment identifiers leaking into a public repo** — an authenticated CLI with live projects exists on the development machine | Medium | Every example value is synthetic and drawn from `synthetic-identifiers.ts`; no real project id, environment name or hostname appears in any artifact; `scripts/audit-synthetic-identifiers.mjs` runs in CI over every human-authored text file. |

## Rollback Plan

All work lands on a branch. `packages/magento-cloud` is new and nothing depends on it, so until publish, rollback is abandoning the branch.

The one shared touchpoint is **`packages/mcp-core`**. The `env` field is optional and additive, so no existing caller changes behaviour and reverting the single commit restores `env: {}` exactly. Revert order matters: revert `packages/magento-cloud` first, then `mcp-core` — reverting `mcp-core` alone breaks the domain package's typecheck loudly rather than silently spawning children with no environment.

`servers.json` / `README.md`: revert the entry and re-run the generator. The README is never hand-edited, so it cannot drift.

**If `@hiberus-magento/magento-cloud` has already been published**, rollback is not unpublish-and-republish: npm never allows reusing a version number. `npm deprecate` the bad version with a message pointing at the fix and ship a patch. Publishing is sequenced last, after every gate is green, precisely so this branch is rarely taken.
