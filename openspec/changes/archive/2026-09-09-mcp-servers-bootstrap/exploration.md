## Exploration: mcp-servers-bootstrap — evidence for the initial proposal

### Current State

Repo is greenfield: remote configured, zero commits, no source. `openspec/config.yaml` already seeds the declared target stack (TS/Node22/ESM, pnpm+turbo+tsup+vitest+eslint+changesets, packages/* = mcp-core, mcp-testing, magento-cloud, eds, aco). This exploration audited three external sources to ground the first real proposal.

### SOURCE 1 — `/Users/ddelgado/Downloads/mcp-magento-cloud-readonly` (fork of a third-party `mcp-magento-cloud`, MIT, by Juan Cinto)

**This fork is already hardened, NOT the naive exec()-based server the brief worried about.** It removed all write tools from upstream and closed a real upstream SQL-validator bypass. `ssh-client.ts` existing is not itself a red flag here — it implements only fixed-binary, argument-validated read operations (see below), not a passthrough.

**18 tools exposed**, all task-shaped (no `magento-cloud <subcommand>` mirroring), split into two families:
- REST-API-backed (genuinely read-only, `apiRequest` rejects any non-GET except one hardcoded SSH-cert-mint POST): `list_projects`, `list_environments`, `get_environment_info`, `get_environment_urls`, `list_activities`, `get_activity_log`, `list_variables`, `list_services`, `get_routes`, `get_app_config`.
- SSH-backed (`ssh-client.ts`, via system `ssh` binary + short-lived cert from `https://ssh.api.magento.cloud/ssh`): `execute_sql` (SELECT/SHOW/DESCRIBE/EXPLAIN/WITH/USE only, single statement, comments rejected outright — not stripped, because MySQL executes `/*! ... */` as real SQL), `list_log_types`, `get_environment_logs` (fixed `tail`/`head` command, log type from a closed enum), `get_environment_relationships`, `read_remote_file` (`cat`/`head`/`tail`, path validated + shell-quoted, no globs/redirects/substitution allowed), `list_remote_directory` (`ls -la`), `search_remote_file` (`grep -F` literal only, never a regex), `get_host_resources` (fixed `df`/`free`/`uptime` string, zero caller input).

**No `ssh` tool, no `tunnel`, no `--` passthrough, no `db:dump` tool exists.** `execSqlViaSsh`/`readFileViaSsh`/etc. each fix the binary as a literal; only validated, shell-quoted arguments vary. This fully satisfies the brief's forbidden list already — the pattern (fixed binary + validated args, never a generic command runner) is exactly what mcp-core should encode as a reusable primitive.

**Command invocation style**: `spawnSync("ssh", [...arrayArgs])` (array form, no shell) for the actual remote command; one **`execSync`** call in `ssh-client.ts:41` (`ssh-keygen -t ed25519 -f "${keyPath}" ...`) and one **`exec`** call in `login.ts:64` (`open "${url}"` / `start "${url}"` / `xdg-open "${url}"`) that build a shell string via template literals. Both interpolate a value the process itself generates (a fixed local tmp path; an OAuth redirect URL built from a fixed template) rather than raw user/tool input, so they are not directly caller-exploitable via MCP tool arguments today — but they are still shell-string interpolation and should be rewritten to `execFile`/array-arg form in the port, not copied as-is, since mcp-core is meant to be the canonical safe pattern.

**Command injection surface, concretely**:
- `ssh-client.ts:41-44` — `execSync(`ssh-keygen -t ed25519 -f "${keyPath}" ...`)`: `keyPath` is `join(tmpdir(), "mcp-magento-cloud-ssh", "id_ed25519")`, not attacker-controlled. Low risk as-is, but a shell-string pattern to not propagate.
- `login.ts:64` — `exec(`${cmd} "${url}"`)`: `url` is `http://127.0.0.1:{port}`, locally generated. Same verdict.
- Everything else in `ssh-client.ts` (`buildReadFileCommand`, `buildListDirCommand`, `buildSearchCommand`, `execSqlViaSsh`) uses a bespoke `shellQuote()` (POSIX single-quote escaping) plus a `validateRemotePath`/`validateQuery` allow/deny-list gate before interpolation into a command string later passed as a single `command` argument to `spawnSync("ssh", [...])`. This is safe against injection on the **remote** shell (ssh always invokes a shell on the far end for the command string) as long as the validators hold; the validators are the real security boundary and are unit-tested (58 tests, `tests/validators.test.js`, `tests/readonly.test.js`, `tests/remote-path.test.js`, `tests/commands.test.js`).

**Reusable for `@hiberus-magento/mcp-core`**:
- `redact.ts` (`redactSecrets`/`redactJson`) — **reuse near-as-is**. Deliberately linear-time regex (avoids ReDoS on MB-scale output), covers key/value secrets and `scheme://user:pass@host` URLs, has a `MCP_MAGENTO_NO_REDACT` escape hatch and a backtracking-safety test. This is exactly the shape of a shared redaction utility other domains (EDS/ACO tokens) will also need.
- `shellQuote()` + the "fixed binary, validated+quoted args, never a generic runner" pattern in `ssh-client.ts` — **reuse the pattern, not the SSH specifics**, as a generic `mcp-core` helper for any future case that must shell out.
- `validators.ts` (`validateQuery`, `validateRemotePath`, `validateLineCount`) — **rewrite as domain-specific validators** informed by this pattern; the SQL comment-rejection-not-stripping lesson and the "validator returns the exact string to execute" contract should become an mcp-core convention/test pattern (a validator must never validate a normalized copy and execute the raw string).
- `login.ts` OAuth2 PKCE browser-login flow (authorization_code + PKCE S256, local loopback server on port 5000-5010, exclusive-login file lock so concurrent processes don't race two browser tabs) — **the login *pattern* is reusable design** (interactive CLI performs login, MCP server only reads token, precedence: direct access token env var > API token env var > stored refresh token > interactive login), matching the brief's mandated auth pattern almost exactly. The magento.cloud-specific OAuth wiring itself is not reusable to EDS/ACO (different auth entirely, see Source 2), but the "coalesce concurrent token refreshes into one shared promise, retry once after 401 by invalidating a generation-stamped cache" logic in `api-client.ts` (`getToken`/`refreshAfter401`/`generation` field) is a good mcp-core building block for any package.
- Test helpers: `scripts/call-tool.mjs` (a minimal stdio JSON-RPC client that lists/calls tools and exits non-zero on tool error) is a good candidate for `@hiberus-magento/mcp-testing`'s conformance-suite CLI harness.

**Dependencies**: runtime deps are only `@modelcontextprotocol/sdk` (^1.12.1, actually resolves to 1.30.0 in node_modules, MIT, Anthropic) and `zod` (^3.25.20, MIT, Colin McDonnell). Both MIT — inside the allowed license set. `pkce-challenge` (MIT) is a transitive dep of the SDK. No native modules anywhere in this tree (`ssh2` was explicitly removed by this fork specifically because it was the only dep with an install script — noted as a decided default in NEXT-STEPS.md). **Bundling caveat**: `@modelcontextprotocol/sdk` itself pulls in `express`, `hono`, `@hono/node-server`, `cors`, `express-rate-limit`, `ajv`, `jose`, etc. as dependencies (it supports HTTP/SSE transports, not just stdio) — a single-file `tsup` bundle for a stdio-only server will need to verify tree-shaking actually drops the unused HTTP-transport code paths, or bundle size could balloon. Worth a scaffolding-phase build-size check.

**Provenance/licensing**: upstream is `mcp-magento-cloud` by **Juan Cinto** (github.com/juan-cinto-infracommerce/mcp-magento-cloud), MIT, `LICENSE` file present and intact with his copyright notice. This fork's own `package.json` correctly declares `forkedFrom` (package/version/commit/url) and `author: "Juan Cinto (upstream); read-only fork maintained internally"`. MIT is permissive and compatible with re-licensing the derivative under Apache-2.0, but **MIT's attribution clause (must include the original copyright notice and permission notice in copies/substantial portions) must be preserved** — the public Apache-2.0 repo will need a NOTICE or THIRD-PARTY-LICENSES entry crediting Juan Cinto's original MIT-licensed work for any code carried over (the redaction pattern, the validated-SSH-command pattern, the token-refresh-coalescing logic), even after it's rewritten into `mcp-core`, if enough original expression survives. #### EDS (`eds-cli/eds.py`) — Edge Delivery Services / AEM Admin API

- **Auth mechanism (verified against official docs, see Source 3)**: a **static bearer-like API key**, sent as `authorization: token <TOKEN>` by default (note: lowercase custom scheme "token", not "Bearer"), or via a fully custom header name if `EDS_AUTH_HEADER` env var is set (some org configs expect a different header name than the code's default). No OAuth exchange, no refresh flow — the credential is presented as-is on every request. Token is read with precedence: `$EDS_TOKEN` env var > macOS Keychain (`security` CLI, service name `eds-token`) > `~/.eds-secrets.json` (mode 0600, JSON, key `token` per profile name) > (falls through to non-interactive "no token" state, degrading to a browser-console JS-generation fallback command that never touches the API key at all). Login is **non-interactive by design** for the token path: the CLI never opens a browser or performs an OAuth dance itself; the operator pastes a token obtained from the AEM admin UI/Sidekick (`pbpaste | eds auth token set`). Profile metadata (org, code repo, backend endpoints) lives in `./eds-profiles.json` (shareable) or `~/.eds-profiles.json`, separate from the secrets file.
- **Base URL**: `https://admin.hlx.page` (constant `ADMIN`).
- **Complete command surface** (resource → verb): `profile {list,add,edit,use,remove}` (local only, no network) · `auth {status, token set, token clear}` · `site {list,show,plan,apply,delete,browser; source show, source set}` · `cdn {show}` · `config {effective,from-file,from-db}` · `version {list,restore}` · `key {list,create,delete}` (`--scope org|site`) · `robots {show}` · `status {show,bulk}` · `preview {show,update,delete,bulk}` · `live {show,publish,unpublish,bulk}` · `cache {purge}` · `index {show,update,delete,bulk}` · `sitemap {rebuild}` · `snapshot {list,show,add,remove,publish,review,delete}` (always on `main`) · `code {show,sync,delete}` · `job {list,show,wait,stop}` · `log {tail}` · `spec {build}` · `dns {list,check}`.
- **Endpoints** (all relative to `admin.hlx.page`, all JSON in/out unless noted): `GET/PUT/POST/DELETE /config/{org}/sites/{site}.json` (site config; PUT creates and 409s if exists, POST updates — CLI does a GET first to choose), `GET /config/{org}/sites.json`, `POST /config/{org}/sites/{site}/cdn/{env}.json`, `GET /config/{org}/sites/{site}/robots.txt` (raw text), `GET/POST /config/{org}/{aggregated|versions}...`, `GET/POST/DELETE /status|preview|live|cache|index|sitemap/{org}/{site}/{ref}{path}` (content operations; bulk variants POST to `.../*` with a `paths` array in the body — **bulk delete has no DELETE endpoint, it's `{"paths":[...], "delete": true}` in the POST body**), `GET/POST/DELETE /code/{owner}/{repo}/{ref}{path}` (code-bus, keyed by GitHub owner/repo not org/site), `GET/DELETE /job/{org}/{site}/{ref}/{topic}/{name}` (bulk-op job polling — **GET on a job returns 202, not 200**, success must be checked as "any 2xx" not `=== 200`), `GET /log/{org}/{site}/{ref}` (audit log, paginated via `nextToken`), `GET/POST/DELETE /snapshot/{org}/{site}/main/{id}...` (snapshots always pinned to `main`), `POST/DELETE /config/{org}[/sites/{site}]/apiKeys.json` (API key mgmt — **value only returned once at creation, never retrievable again**).
- **Pagination**: cursor-style via `nextToken` on the log endpoint only; other list endpoints are unpaginated (bounded domain: 32 sites, 63 catalog views).
- **Rate limiting**: self-imposed client-side throttle of ~10 req/s per project (`MIN_GAP = 0.12s` between calls, sleeps to respect it) — this is **the CLI voluntarily respecting a documented API limit**, not something the server enforces via headers the CLI reads. **429 vs 503 disambiguation is undocumented-but-inferred**: a raw `429` means the CLI's own Admin API rate limit was exceeded; a `503` whose `X-Error` header contains the literal substring `"(429)"` means the *content source* (not the Admin API) rate-limited the request — the CLI greps the error header text for this to give an accurate message. This distinction is not stated anywhere in Adobe's docs; it was reverse-engineered from operational experience and is the single most valuable piece of undocumented behavior in this codebase.
- **Error handling on 401/403/404/429/5xx**: no automatic retry or refresh anywhere (befitting a static, non-expiring-in-practice API key) — every non-2xx just surfaces `HTTP {status}: {body}` to the operator, with a few resource-specific hints (`auth status` interprets 401/403/404 into "token inválido", "sin alcance", "no existe"; `index show` explains a 404 as "not in any index definition"; `snapshot remove/delete` explains 409 as "locked or not empty").
- **Undocumented Admin API traps the CLI already encodes** (valuable for the TS port's conformance fixtures): PUT-creates/POST-updates dichotomy; job GET returns 202; `index bulk` with no body reindexes the entire published site (CLI requires an explicit `--all` flag); bulk write calls silently ignore `/.helix/config` and `redirects.json` (must be published individually); publish/unpublish already purge CDN (so `cache purge` is a distinct, rarer operation); `code` endpoints key by GitHub owner/repo, not org/site; snapshots are hardcoded to `main`; a bulk snapshot POST with an empty body and no `content-type` header is interpreted as "add everything" (the CLI always sends a JSON body to avoid this).
- **Hard-to-reproduce faithfully in TS**: (a) the macOS-Keychain-via-`security`-binary fallback is macOS-only and shells out to a system binary — a TS port should probably drop native-keychain support per the brief's own "no native keychain dependency" constraint rather than port it; (b) the "browser console JS generator" escape hatch (`site browser`) that emits a `<script>` for pasting into devtools when no API key is available — this is a legitimate but unusual auth bypass path that has no clean MCP-tool equivalent (an MCP tool can't drive a human's authenticated browser session) and should probably be explicitly out of scope for the TS `eds` package rather than half-ported.

#### ACO (`aco-cli/aco.py`) — Adobe Commerce Optimizer

- **Auth mechanism (verified against official Adobe docs, see Source 3)**: **full Adobe IMS OAuth2 `client_credentials` server-to-server flow.** Token endpoint `https://ims-na1.adobelogin.com/ims/token/v3` (POST, `application/x-www-form-urlencoded`, `grant_type=client_credentials&client_id=...&client_secret=...&scope=...`). Scope requested by this CLI: `"openid,AdobeID,profile,email,commerce.aco.admin,commerce.aco.ingestion"`. The resulting Bearer token is a JWT; the CLI decodes its claims client-side (base64url, no signature verification — it trusts the issuer) to compute expiry (`created_at + expires_in`) and to display `scope`/`client_id`/`user_id`. **There is no refresh-token grant** — Adobe IMS server-to-server tokens are re-minted from the client_id+secret on every expiry, not refreshed; the CLI's own comment ("hoy solo trae el Bearer de sesión del Studio — caduca en horas y hay que renovarlo a mano") reveals the admin-scope token is **not even obtainable via client_credentials in this operator's actual setup** — in practice they paste a short-lived Studio session Bearer manually (`aco auth token set`) because the client_credentials grant for `commerce.aco.admin` wasn't working/available for their tenant, while the separate Merchandising (storefront/catalog-query) API uses a **different, longer-lived "restricted access key"** that does NOT depend on that admin Bearer at all. Credential storage: env vars (`ACO_TENANT`, `ACO_REGION`, `ACO_CLIENT_ID`, `ACO_ORG_ID`, `ACO_TOKEN`, `ACO_CLIENT_SECRET`) > `~/.aco-profiles.json` (non-secret profile metadata: tenant, region, client_id, org_id) + `~/.aco-secrets.json` (mode 0600: client secret and/or a manually-set Bearer token) > macOS Keychain fallback (service `aco-client-secret`). Non-interactive: no browser flow anywhere in this CLI; `client_secret`/token are always supplied out-of-band (env, paste, or prior `profile add` prompt).
- **This makes ACO auth strictly harder to implement than EDS**: it needs an OAuth2 client_credentials token-exchange client, JWT claims decoding for expiry tracking, two independent credential tracks (admin Bearer vs. Merchandising restricted-access-key) with different lifetimes and different failure modes, and — per the CLI's own real-world experience — the "official" grant may not even work for the admin scope in practice, requiring a manual-paste fallback path as a first-class feature, not just a dev convenience.
- **Base URLs**: `https://{region}.api.commerce.adobe.com/{tenant}/admin/graphql` (admin, GraphQL, Bearer + `x-api-key: {client_id}` + `x-gw-ims-org-id: {org_id}`) and `.../{tenant}/graphql` (Merchandising, GraphQL, headers `AC-View-ID`/`AC-Scope-Locale`/`AC-Price-Book-ID` instead of a Bearer — restricted-access-key model, no admin auth needed).
- **Complete command surface**: `profile {list,add,edit,use,remove}` · `auth {status; token set, token clear}` · `source {list}` (catalog sources/locales) · `pricebook {list --tree}` · `key {list}` (restricted access keys) · `view {list --all, count, prune --yes, delete --yes}` (catalog "channels") · `policy {list, init, delete --yes, enable/disable --all|names --yes}` (catalog filtering rules) · `attribute {list, values}` (indexed-catalog attribute inspection via Merchandising API facets) · `provision [--only vertical] [--store-view] [--skip-check] --yes` (idempotent multi-step: validate attribute → create/update policies → create/update catalog views → verify) · `api query [--merchandising] [--view-id] [--locale]` (raw GraphQL escape hatch).
- **All mutating GraphQL** goes through a small fixed set of mutations: `createChannel`/`updateChannel`/`deleteChannel`, `createPolicy`/`updatePolicy`/`deletePolicy` — every write in this CLI is really one of these six operations, parameterized.
- **Pagination**: cursor-style `scrollId` on `priceBooks` only (loops until `scrollId` is empty or a page returns no items); everything else is unpaginated (tenant catalog sizes are small).
- **Rate limiting**: no client-side throttle at all in `aco.py` (unlike EDS) — a `time.sleep(0.3)`/`time.sleep(0.4)` appears only between individual mutation calls in bulk loops (`view prune`, `policy toggle`, `provision`), as a courtesy pace, not a measured/documented rate limit.
- **Error handling on 401/403/404/429/5xx**: GraphQL error handling is uniform — Adobe wraps failures as HTTP 200 with a GraphQL `errors[]` array (not always as HTTP status codes); the CLI checks `out.get("errors")` first and only falls back to `HTTPError`/`URLError` for actual transport failures. No automatic retry, no backoff, no distinct 429 handling — Adobe's error payload sometimes carries a `classification`/`code` extension the CLI surfaces verbatim, and it pattern-matches the error message text for `permission|scope|unauthor|forbidden` to print an extra "you probably need `commerce.aco.admin`" hint. This is materially less defensive than EDS's error handling.
- **Hard to reproduce faithfully in TS**: (a) client-side JWT claim decoding without signature verification is a legitimate, low-stakes UX feature (just showing expiry) but a TS port must be careful not to imply it validates anything; (b) the dual-credential model (admin Bearer vs. Merchandising restricted key) with independent expiry and independent failure UX needs to be modeled as two auth tracks in the TS client, not one; (c) the "Studio session Bearer, pasted manually because client_credentials didn't actually work for admin scope in this tenant" reality is an operational finding, not a documented API contract — the TS `aco` package's proposal should treat "does client_credentials actually issue a token with `commerce.aco.admin` scope for our tenants" as an open validation question before committing to auto-refresh-via-client-credentials as the only supported admin-auth path.

#### `shared/`

Contains exactly one file: `catalog-views.csv` (63 rows: vertical, store_view, ac_view_id, ac_price_book_id, currency, locale). It is a **data hand-off artifact between the two CLIs**, not code: `eds spec build` creates the rows, `eds config from-file`/`from-db` fills in locale/currency, `aco provision` fills in `ac_view_id`, and `eds site apply` consumes those `ac_view_id`s to build each site's `public` block. There is no shared *code* module — "shared" here is purely a shared CSV contract. This means there is no natural "shared business logic" to port into a TS `shared` package; the only thing worth generalizing into `mcp-core` is the *pattern* (a CSV/JSON hand-off file bridging two domain packages), not any code.

### SOURCE 3 — Adobe documentation (verified)

- **EDS Admin API auth** ([aem.live/docs/admin-apikeys](https://www.aem.live/docs/admin-apikeys)): confirmed **static API keys**, sent via `X-Auth-Token` header or `Authorization: token <key>`. "Function similarly to a password." No OAuth exchange. Keys are created via `POST /config/{org}/sites/{site}/apiKeys.json`, returned once and never retrievable again, and have an expiration (typically ~1 year) — matches the Python CLI's implementation exactly.
- **ACO auth** ([developer.adobe.com/.../server-to-server](https://developer.adobe.com/commerce/webapi/rest/authentication/server-to-server), [developer.adobe.com/commerce/services/optimizer/data-ingestion/authentication](https://developer.adobe.com/commerce/services/optimizer/data-ingestion/authentication)): confirmed **Adobe IMS OAuth2 client_credentials**, token endpoint `https://ims-na1.adobelogin.com/ims/token/v3`, requires client_id + client_secret + org_id + scope (docs mention `commerce.accs` and related scopes for the broader Commerce API family; the Python CLI additionally requests `commerce.aco.admin`/`commerce.aco.ingestion`), Bearer tokens valid ~24h with no refresh-token grant — re-mint from client_id/secret on expiry, matching the Python CLI's model and confirming its "no refresh flow" behavior is correct, not a shortcut.
- **MCP stdio auth guidance** (modelcontextprotocol.io, official spec discussion): confirmed — "Implementations using an STDIO transport SHOULD NOT follow this [OAuth] specification, and instead retrieve credentials from the environment." This directly validates the brief's mandated pattern (CLI performs interactive/manual login and persists the token; MCP server only reads it, precedence env var > config file, never prompts).
- **Conclusion — which of EDS/ACO has simpler auth, with evidence**: **EDS is simpler**, decisively. EDS needs only: read a static string from env/config, attach it as one header, done — no expiry tracking, no token exchange client, no dual-credential model. ACO needs: an OAuth2 client_credentials HTTP client, JWT decoding for expiry, handling of the fact that the officially-documented grant may not actually work for the admin scope in a given tenant (requiring a manual-Bearer-paste fallback as a supported path, not an edge case), AND a second, independent, differently-shaped credential (Merchandising restricted access key) for half its command surface. This confirms the brief's assumption and validates building `eds` as domain package #2, `aco` as #3.

### Scope Decomposition (validating/refining the brief's stated order)

The brief's order — (1) scaffolding, (2) simpler-auth domain, (3) other domain, (4) magento-cloud, (5) Dockergento — is **validated by evidence, with one refinement**:

1. **Scaffolding** (root config, pnpm/turbo/tsup/vitest/eslint wiring, CI, `mcp-core` skeleton with the redaction/shell-safety/token-refresh-coalescing/credential-precedence patterns extracted from Source 1, `mcp-testing` conformance-suite skeleton, `servers.json` manifest + README generator). No domain logic yet. This is the correct first change — everything downstream depends on `mcp-core`'s credential-loading and redaction primitives existing first.
2. **`eds` package** — confirmed simplest auth. Depends only on scaffolding. The conformance-suite "cold start" cost is paid here first.
3. **`aco` package** — harder auth (OAuth2 client_credentials + dual-credential model). Depends on scaffolding; does *not* depend on `eds` code, but the `catalog-views.csv` hand-off pattern between them is worth documenting as a cross-package integration note even though it's not a code dependency. Note: `eds site apply` consumes `ac_view_id`s that `aco provision` produces — if the TS ports ever need an end-to-end conformance scenario, it will need both packages, which argues for sequencing `aco` immediately after `eds` (as the brief already says) rather than interleaving `magento-cloud` between them.
4. **`magento-cloud` package** — Source 1 gives this a massive head start: 18 tools, hardened, tested, MIT-licensed with clear attribution obligations already identified above. This is really "port + relicense + attribute + integrate into monorepo conventions," not "design from scratch," so despite being 4th it may be lower-effort than `aco`. Recommend keeping it 4th as the brief states, but flag it as a strong candidate to *not* be the largest change in the roadmap.
5. **Dockergento integration** — not explored (out of scope for this exploration; no source material was provided for it). Flag as needing its own exploration pass before being proposed.

### Cassette Recording Feasibility (mitmproxy against the Python CLIs)

**Feasible for EDS, feasible-with-more-care for ACO:**
- EDS: plain HTTPS to a single host (`admin.hlx.page`), simple JSON/text bodies, static-token auth. Recording real traffic and scrubbing is straightforward: scrub the `authorization`/`x-auth-token` header value, and scrub org/site names if they're considered sensitive (they appear in URLs and response bodies, e.g. the real org and site slugs — these are real customer identifiers present throughout `eds.py`'s `DEFAULTS` and `VERTICALS`, so cassettes must not carry them into a public repo verbatim; use synthetic org/site names in fixtures).
- ACO: two hosts (IMS token endpoint + `{region}.api.commerce.adobe.com`), GraphQL bodies (queries are static strings in the CLI, but variables carry tenant-specific data: policy names, attribute values, price book IDs). Scrubbing needs to cover: the `Authorization: Bearer <jwt>` header, `x-api-key`/`x-gw-ims-org-id` headers, the client_credentials POST body (`client_id`/`client_secret` in form-urlencoded, not JSON — mitmproxy scrubbing rules must handle both content types), and tenant-identifying strings inside GraphQL variables/responses (channel names embed vertical names like `futbol-...`, real business data).
- **Real friction**: both CLIs talk to production-adjacent tenants with real customer data (the customer actual catalog/site structure) — recording "real API traffic" as literally proposed risks baking real business identifiers into public test fixtures even after credential scrubbing, which credential-focused mitmproxy scrubbing rules won't catch (that's data scrubbing, a different and harder problem: recognizing which fields are secrets vs. which are merely non-public business data).
- **Lower-friction alternative that preserves verification value**: record cassettes once against a **sandbox/test tenant with synthetic data** (ACO already has a documented `na1-sandbox` region convention visible in `eds.py`'s `DEFAULTS["aco_pre"]`) rather than the real the customer tenant, or hand-author fixture JSON directly from the *shapes* verified in Source 3's official docs + the Python code's own response-parsing logic (which the Python code already documents precisely: `channels{...}` shape, `productSearch{...}` shape, job `202` envelope, etc.) without ever touching mitmproxy against production. This trades "byte-for-byte real traffic" for "schema-accurate synthetic traffic," which is very likely sufficient given the response shapes are already fully known from reading the CLI source, and removes the customer-data leak risk entirely. Recommend this as the default; reserve real mitmproxy recording (against sandbox only) for the specific undocumented behaviors this exploration flagged (429 vs 503-with-"(429)" disambiguation, job 202 envelope, PUT-409-vs-POST semantics) where exact byte-for-byte behavior matters more than typical CRUD shapes.

### Tool Design Sketch (task-shaped, grounded in source — not one-tool-per-subcommand)

- **`eds` package** (simplest domain, ~6-8 tools covering ~19 CLI resources): `eds_get_site_status` (wraps `status show` + `preview/live show`, one call for the "where does this page stand" question), `eds_publish_path` / `eds_unpublish_path` (wraps `live publish`/`unpublish`, single or bulk via an array param, subsuming `--wait` polling internally), `eds_list_sites`, `eds_get_site_config` (wraps `site show` + `cdn show` + `config effective`), `eds_reindex` (wraps `index update`/`bulk`, with the `--all` full-reindex danger gated behind an explicit confirm-shaped argument, not a hidden flag), `eds_get_audit_log` (wraps `log tail`), `eds_manage_snapshot` (wraps the snapshot lifecycle as one tool with a `verb` enum, since it's a closed, cohesive state machine). Explicitly **out of scope for MCP tools**: `site apply`/`site delete`/`key create` (org-structural, high-blast-radius, better left to the human CLI) and the `browser` JS-generator escape hatch (has no MCP equivalent).
- **`aco` package** (~5-6 tools): `aco_query_catalog` (wraps the Merchandising API read path: `attribute list/values`, `view count`, ad-hoc read-only GraphQL — this is the safe, read-heavy half of the CLI and the natural first MCP surface), `aco_list_catalog_views`, `aco_list_policies`, `aco_toggle_policy` (wraps enable/disable, gated), `aco_get_provisioning_plan` (wraps `provision` in dry-run/plan mode only — never auto-apply from an agent without an explicit confirm path, mirroring the CLI's own `--yes` gate). `provision --yes` and `view/policy delete` are candidates to stay CLI-only initially given their write-heavy, cross-cutting nature.
- **`magento-cloud` package**: Source 1's existing 18-tool set is already close to ideal task-shaping and should be the starting point almost as-is (list/environment/activity/log/variable/service/route/config read tools, plus the validated SQL/file/dir/search/host-resource SSH tools) — the main work here is porting the *pattern* (mcp-core primitives) rather than redesigning the tool surface.

### Risks and Open Questions

1. **Concrete auth mechanism for EDS/ACO** — RESOLVED by this exploration and Source 3 verification (see above): EDS = static API key/header; ACO = IMS OAuth2 client_credentials + separate restricted-access-key track, with an unresolved question of whether client_credentials actually issues admin-scoped tokens in the target tenants (the Python CLI's own comments suggest it may not, in practice, for this operator).
2. **Cold-start threshold for the conformance suite** — still OPEN. Needs a decision in `sdd-propose`: how many packages/tools must exist before `mcp-testing`'s CI gate becomes mandatory-blocking vs. advisory-only, since package 1 (`eds`) will be the one paying for building the suite from nothing.
3. **`@modelcontextprotocol/sdk` bundle-size risk** — the SDK pulls in a full HTTP server stack (express/hono/cors) even for stdio-only servers; must verify tsup/esbuild tree-shaking actually produces a lean single-file bundle before committing to "single bundled file, `dependencies: {}`" as a hard constraint across all packages.
4. **MIT attribution obligation** — the Apache-2.0 public repo must carry a NOTICE/THIRD-PARTY-LICENSES entry for Juan Cinto's original `mcp-magento-cloud` (MIT) for any pattern/code carried into `mcp-core` or the `magento-cloud` package, even after rewriting.
5. **Real customer/business data exposure risk** — Source 2 code and its READMEs contain real customer identifiers (real org slugs, real site slugs, and real production domains, plus real DNS/hosting details — deliberately not reproduced here) baked into the CLI's own constants (`VERTICALS`, `DEFAULTS`, `BACKEND_HOSTS`). None of this may be copied verbatim into the public `mcp-servers` repo's fixtures, tests, docs, or examples — the TS port's fixtures must use synthetic domains/org names throughout.
6. **Unconfirmed presence of live credential files on this machine** — `~/.eds-secrets.json`, `~/.aco-secrets.json`, `~/.eds-profiles.json` were not confirmed absent (a recursive home-directory scan timed out and was not retried); if present, they contain live Adobe/EDS credentials and must never be referenced, opened, or copied by value in any subsequent SDD phase.
7. **Sequencing risk in `aco provision`'s tight coupling to `eds`'s `catalog-views.csv`** — while not a code dependency, an end-to-end conformance scenario spanning both domains will need synthetic fixtures for this hand-off file; worth deciding in `sdd-propose` whether that cross-domain scenario belongs to the `eds` change, the `aco` change, or a later integration change.
8. **Dockergento integration (step 5) has zero source material explored** — needs its own `sdd-explore` pass before it can be proposed; nothing in this exploration should be read as covering it.

### Recommendation

Proceed to `sdd-propose` for the **scaffolding change first** (step 1 of the 5-step decomposition), using this exploration's `mcp-core` primitive list (credential precedence loader, redaction, shell-safety helper, token-refresh coalescing, validator contract of "return the exact string to execute") as its concrete design input. Sequence `eds` next (confirmed simpler auth), then `aco`, then `magento-cloud` (port of Source 1, with required MIT attribution), then a separately-explored Dockergento integration change.

Yes, for the scaffolding change and for the `eds`-then-`aco`-then-`magento-cloud` sequencing decision. The orchestrator should present risk items 2 (conformance cold-start threshold), 4 (MIT attribution mechanics), and 7 (cross-domain fixture ownership) as explicit decisions for `sdd-propose` to resolve rather than assume.

## Key Learnings

1. The audited magento-cloud MCP fork is already hardened (no ssh/tunnel/passthrough/db:dump tools) and its "fixed binary + validated args" pattern is the reusable mcp-core primitive, not the SSH code itself.
2. EDS Admin API auth is a static API key/header with no OAuth exchange; ACO requires full Adobe IMS OAuth2 client_credentials plus a second independent Merchandising restricted-access-key track, confirming EDS as the simpler-auth domain to build second.
3. Adobe's official docs confirm both CLIs' auth models exactly, and the MCP spec explicitly directs stdio-transport servers to read credentials from the environment rather than negotiate OAuth interactively.
4. Both Python CLI trees contain real customer business identifiers (the customer domains, org names) that must never be copied verbatim into the public repo's fixtures or docs.
5. The MCP TypeScript SDK dependency pulls in a full HTTP server stack (express/hono), which is a bundle-size risk for the "single-file, dependencies: {}" packaging constraint that the scaffolding phase must verify.
