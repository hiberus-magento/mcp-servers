## Exploration: aco-package (Change 3 of 5) — ACO CLI + MCP server

### Current State

**Reused foundation (verified by reading real code, not specs alone):**
- `packages/mcp-core/src/credentials/token-provider.ts` already ships TWO `TokenProvider` implementations: `StaticTokenProvider` (used by `eds`, no expiry) and `MintedTokenProvider` — expiry-aware, single-flight-coalesced, generation-stamped, with a required `mintTimeoutMs` and an optional `skewMs`. `MintedTokenProvider` is UNUSED by `eds-package` (grep of `openspec/changes/archive/2026-09-10-eds-package/design.md` for "Minted"/"IMS"/"aco" returns nothing) — it was built speculatively in change 1 (bootstrap) and `aco-package` would be its first real consumer.
- `token-provider.ts` also already exports `CredentialExpiredError` (parallel to `MissingCredentialError`), unused by `eds` (its static key never expires). This is the exact shape an expiring Bearer needs.
- `credentials/resolve.ts`: env-var-over-file precedence, `0600`/`0700` enforcement, atomic write, refuses to *read* a loose-permission file (throws `LooseCredentialFilePermissionsError` instead of warning).
- `credentials/cli.ts`: `--token` flag is structurally absent from the parser; only stdin/env accepted.
- Domain wiring pattern (`packages/eds/src/credential-provider.ts`): construct the `TokenProvider` ONLY in the adapter layer (`cli.ts`/`mcp.ts`), never inside `client/`; supply a `Remedy` naming the domain's own out-of-band bootstrap step.
- `packages/eds/src/tools/eds-tools.ts` is the concrete precedent for thick, task-shaped tools: 9 tools, `defineTool()` with mandatory annotations, a nested-`discriminatedUnion`-under-`request` hazard gate (`eds_reindex`'s full-site branch), and `nonEmptyPaths` (`z.array(...).min(1)`) on every bulk-write array.
- `servers.json` and `catalog-views.csv` (`packages/mcp-testing/src/fixtures/`) — the cross-domain contract. **Column-shape gap found**: the committed fixture's header is `vertical,site,locale,view_code`. The Python CLI's `provision` reads/writes a CSV shaped `vertical,store_view,ac_view_id,ac_price_book_id,currency,locale` (see `views_rows()`/`view_name()`/`c_provision` in `aco.py`). These are NOT the same shape — `site` vs `store_view`, `view_code` vs `ac_view_id`, and the fixture is missing `ac_price_book_id`/`currency` entirely. The "aco provisions `ac_view_id`, eds consumes it" hand-off described in the brief cannot work against the current fixture without a schema change to `catalog-views.csv` (additive columns, or a rename) — this is `aco-package`'s job to resolve, not a pre-existing bug.
- Cold-start budget (`packages/mcp-testing/src/conformance/cold-start.ts`): `COLD_START_BUDGET_MS = 250`, explicitly PROVISIONAL (local-machine p95, not CI), with a documented re-measure trigger: real CI numbers become available, OR bundle size moves >20%. `aco`'s bundle is a new, likely differently-shaped bundle (Python CLI has ~9 GraphQL operations plus a `provision` orchestration — comparable in kind to `eds`'s bundle), so it should REUSE the existing provisional threshold rather than closing the CI-measurement gap itself; closing that gap is orthogonal infrastructure work (a `workflow_dispatch` job), not part of this change's scope, unless `aco`'s actual measured bundle size differs from `eds`'s by >20%, in which case the spec's own re-measure trigger fires and a new local-provisional number should be recorded the same honest way `eds` did.

### The credential question — settled with a loud finding and one open question

**Loud finding (positive): `mcp-core` needs ZERO changes for the admin track.** `MintedTokenProvider` already has everything an IMS `client_credentials`-minted, expiring token needs: an async `mint()` hook, `mintTimeoutMs` (required, no default — a hung IMS call fails fast), `skewMs` for early-refresh margin, single-flight coalescing (two concurrent tool calls do not double-mint), and per-generation `invalidate()` (a 401 invalidates only the generation that produced it, not a token minted after). This is a precise fit for `client_credentials` re-minting with no refresh grant. `CredentialExpiredError` is the correct, already-generic error class for an admin Bearer that the JWT claims say has expired — no domain-specific subclass needed.

Concretely, `aco`'s admin-track `credential-provider.ts` should:
1. Try `MintedTokenProvider` wrapping a `mint()` that POSTs `client_id`/`client_secret`/`scope`/`grant_type=client_credentials` (form-urlencoded) to `https://ims-na1.adobelogin.com/ims/token/v3`, IF a client id/secret pair is configured. This mirrors the CLI's own `token()` function.
2. Because the CLI's own comments record that `client_credentials` did NOT work for `commerce.aco.admin` in the operator's tenant, this path may legitimately fail with a permission/scope error at mint time — that failure should surface as `MissingCredentialError` naming the manual-paste remedy, not a generic network error.
3. Manual paste (`aco auth token set` reading stdin, exactly like `eds`) is the SUPPORTED fallback, not a dev convenience, and needs no new provider shape: a thin ACO-specific wrapper (parallel to `eds`'s `resolveEdsCredentialDirect`) decodes the JWT's `created_at`/`expires_in` claims **without signature verification** (exactly what the Python CLI does in `jwt_claims`/`jwt_left`) purely to compute an expiry, and throws the existing `CredentialExpiredError` before the request layer ever sends a stale Bearer. This requires zero new mcp-core primitives — it is domain code composing two already-exported error classes.

**Open question the programme's stated architecture may need to revisit — flag for the proposal phase, do not resolve here:** the brief describes the Merchandising track as "a long-lived restricted access key" sent as static headers with no Bearer. Reading the CLI's actual `merch()` calls (`_post(CTX["merch"], query, None, extra, admin=False)`) shows **zero secret material of any kind** is sent to the Merchandising endpoint — only `AC-View-ID` / `AC-Scope-Locale` / (optionally) `AC-Price-Book-ID`, which are routing parameters, not credentials. This is because every catalog view this CLI provisions is created with `protectionEnabled: false` (see `c_provision`'s `req = {... "protectionEnabled": False ...}`). Adobe's own documentation (verified below) describes a genuinely different mechanism for a PROTECTED catalog view: generate an RSA key pair (2048–8192 bits), register the PUBLIC key in Optimizer Studio as a "restricted access key," keep the PRIVATE key locally, and **sign a JWT per request** (`AC-Catalog-View-Access-Token` header, RS256-verified server-side) — not paste a static long-lived string into a header. There is no evidence in either the CLI or Adobe's docs of a bare static "restricted access key" value that goes directly into a header with no signing step. Two real possibilities: (a) the operator's tenant only ever queries unprotected views, so the "second credential track" for MVP scope is actually "no credential, just a view-id routing parameter" — a much smaller `TokenProvider` surface (arguably none needed) than currently assumed; or (b) a future/complete `aco-package` scope needs genuine per-request RSA-JWT signing, which is a materially different and more complex primitive than anything `mcp-core` currently has (`StaticTokenProvider`/`MintedTokenProvider` both hand back a plain bearer string; neither signs a fresh JWT per outgoing request from a locally held private key). **This distinction changes the credential-loading design meaningfully and should be a proposal-phase decision, not assumed.**

### Day-one bootstrap, step by step

**Admin track:**
1. (Adobe UI, outside this package) Operator creates a project in Adobe Developer Console, adds an OAuth Server-to-Server credential, and is shown a client id + client secret once.
2. (Adobe UI, outside this package) Operator determines whether `commerce.aco.admin` is grantable to that credential in their org/tenant — the CLI's own field experience says it often is NOT, in which case the operator instead opens Adobe Commerce Optimizer Studio, authenticates interactively, and copies a short-lived session Bearer (via browser devtools/network tab — no documented API mints this directly).
3. `hiberus-aco auth token set` reads that Bearer from stdin (or `--client-secret`-driven `MintedTokenProvider` attempt first, per above), persists to `$XDG_CONFIG_HOME/hiberus/aco.json` at `0600`.
4. Every admin write from the CLI resolves this credential per-call; on expiry (`CredentialExpiredError` from decoded claims, or a live 401), the CLI names the exact remedy: re-paste from Studio, or re-attempt client-credentials mint.

**Merchandising track:**
1. (Adobe UI, outside this package, only if the protected-catalog interpretation above is confirmed) Operator generates an RSA key pair, registers the public key in Optimizer Studio against a specific catalog view (max 3 keys per view, max 100 per environment, ~5 minute revocation propagation per Adobe's docs).
2. If the unprotected interpretation holds instead (matches the actual reverse-engineered CLI), there is no step 1 — the MCP server only needs `AC-View-ID`/`AC-Scope-Locale`/optional `AC-Price-Book-ID` as plain call parameters (from `catalog-views.csv` or tool arguments), sourced with zero secret material.
3. Either way, `EDS_ORG`-style env vars (`ACO_TENANT`, `ACO_REGION`) are needed to build the base URL `https://{region}.api.commerce.adobe.com/{tenant}/graphql` — these are configuration, not credentials, and fit `mcp-core`'s existing precedent of adapter-level `process.env` reads (see `createRuntimeResolver()` in `eds-tools.ts`).

### How the two tracks fail differently

- **Admin track**: `401`/`403` from the admin GraphQL endpoint (wrapped in HTTP-200 GraphQL `errors[]` — see below) → actionable remedy naming BOTH options (re-attempt mint, or re-paste from Studio) because unlike `eds`, there is no single "run this one command" fix. A scope-related failure should be pattern-matched the way the CLI already does (`permission|scope|unauthor|forbidden` in the error message) and given a distinct, more specific remedy: "the admin API requires scope `commerce.aco.admin`; if `client_credentials` cannot obtain it in this tenant, paste a Studio session Bearer instead."
- **Merchandising track**: if unprotected, failures are ordinary GraphQL data errors (bad `AC-View-ID`, bad locale) with no credential-remedy framing at all. If protected (JWT-signing interpretation confirmed), failures split into "key not registered/revoked" (data-plane, actionable: re-register key in Studio) vs. "signature/clock skew" (client-side bug, not a credential problem) — these are two different failure classes that a single generic `MissingCredentialError` would blur.

### 1. Python `aco-cli` — GraphQL operations, error model, pagination, rate limiting

**Operations (all six confirmed, no more, no less):**
- `Q_SOURCES` — `{ scopes { locale } }` (admin).
- `Q_VIEWS` — `channels { channelId name scopes{locale} defaultPriceBookId allowedPriceBookIds policyIds restrictedAccessKeyIds protectionEnabled layers{order scope{locale layer}} }` (admin).
- `Q_POLICIES` — `policies { policyId name mandatory actions{ triggers{name transportType} filters{attribute values value enabled actionFilterOperator valueSource} } }` (admin).
- `Q_PBOOKS` — `priceBooks(size,searchTerm,scrollId){ items{id name currency level parentIds} scrollId }` (admin) — **the only cursor-paginated query, confirmed**; `scrollId` round-trips exactly like EDS's `nextToken` pattern.
- `Q_KEYS` — `restrictedAccessKeys { keyId title expirationDate }` (admin) — confirms restricted access keys DO have an `expirationDate`, i.e. they are not eternal, reinforcing the "not a simple static long-lived value" read above.
- Six mutations, confirmed exactly as the prior exploration suggested and no others exist anywhere in the file: `createChannel`/`updateChannel`/`deleteChannel` (`M_VIEW_NEW`/`M_VIEW_UPD`/`M_VIEW_DEL`) and `createPolicy`/`updatePolicy`/`deletePolicy` (`M_POL_NEW`/`M_POL_UPD`/`M_POL_DEL`).
- Merchandising queries are ad hoc GraphQL strings built inline (`productSearch(phrase, page_size, current_page){ total_count facets{attribute title buckets{...}} items{productView{attributes(roles:[]){name value}}} }`) — there is no separate merchandising "operations catalog" the way there is for admin; it's closer to a raw pass-through, which the CLI's own `api query --merchandising` escape hatch acknowledges.

**Base URLs & headers:**
- Admin: `https://{region}.api.commerce.adobe.com/{tenant}/admin/graphql`. Headers: `Content-Type`, `Accept`, `User-Agent`, `Authorization: Bearer <token>`, optionally `x-api-key: <client_id>`, optionally `x-gw-ims-org-id: <org_id>`.
- Merchandising: `https://{region}.api.commerce.adobe.com/{tenant}/graphql`. Headers: `Content-Type`, `Accept`, `User-Agent`, `AC-View-ID`, `AC-Scope-Locale`, optionally `AC-Price-Book-ID`. **No Authorization header of any kind is ever sent by this CLI to this endpoint** (see credential open question above).

**Error model (confirmed, both wrapping styles present and distinct):**
- HTTP-level failures (`urllib.error.HTTPError`) surface as a raw status + truncated body — these come from the transport itself (e.g. genuinely unreachable, 500s that never form a valid JSON-RPC/GraphQL envelope). Network failures (`URLError`) get a distinct "check your region" remedy.
- Successful-transport-but-failed-operation is HTTP 200 with a top-level `errors[]` array (`_post`'s `out.get("errors")` branch) — this is Adobe's GraphQL error convention exactly as the brief predicted. The CLI extracts `errors[0].message` and, if present, `extensions.code` or `extensions.classification`, appending it in brackets to the message. **A TS client MUST branch on `body.errors` presence regardless of the HTTP status code** — status-code-only error handling silently swallows this class of failure.
- The CLI additionally pattern-matches the error MESSAGE TEXT for the substrings `permission|scope|unauthor|forbidden` to append a scope-specific hint — this is a heuristic, not a structured signal from Adobe (no dedicated error code confirms scope-vs-generic-permission failures); a TS client should keep this as a best-effort classifier, not treat it as authoritative.

**Rate limiting (confirmed): NO client-side throttle exists.** The only pacing is `time.sleep(0.3)` between deletes in `view prune`, `time.sleep(0.3)` between policy-carrying view updates in `provision`, and `time.sleep(0.4)` between view creates in `provision` — fixed courtesy delays, not adaptive, not response-header-driven, and not present at all on read paths. **Recommendation for the TS client**: do NOT port fixed sleeps. Reuse EDS's `TokenBucketRateLimiter` pattern (already in `packages/eds/src/client/rate-limiter.ts`) sized conservatively for bulk mutation loops (e.g. one bucket for `provision`'s create/update fan-out), and treat any GraphQL `errors[]` entry whose `extensions.code`/`classification` looks throttle-shaped as a distinct error class the same way EDS's `mapThrottle` distinguishes `429` from `503+x-error`. Since Adobe's admin API returns throttle signals (if any) as HTTP-200 GraphQL errors rather than a `429` status, `aco`'s throttle detection must be built on parsing `errors[].extensions`, not on HTTP status codes at all — structurally different from EDS's `mapThrottle`, which is entirely status-code-driven.

**`provision` — mapped precisely (four numbered steps in the CLI's own output, `1/4`–`4/4`):**
1. **Validate attribute** (skippable via `--skip-check`): pick any already-provisioned view for the target locale, query one Merchandising facet for the configured `attribute`/`value` pair per vertical, and abort BEFORE writing anything if any vertical's expected value has zero matching products (prevents creating catalog views that would be empty).
2. **Create/update policies**: for each vertical's row in the local policy CSV, create the named policy if it doesn't exist (`createPolicy`), or record its existing `policyId` if it does — this step is deliberately idempotent purely by name lookup (`have = {p["name"]: p for p in ...}`), never by comparing filter contents.
3. **Create/update catalog views**: for each `(vertical, store_view)` pair still needing a view, resolve its price-book family (`pb_family`, walking `parentIds`), and either create (`createChannel` then a follow-up `updateChannel` to attach `defaultPriceBookId` — TWO calls, not one, because `createChannel`'s own response doesn't accept `defaultPriceBookId` as an input in the same mutation per this CLI's usage) or, if the view exists but its `policyIds` differ from the target, `updateChannel` to attach the policy. Existing correct views are a no-op ("=").
4. **Verify**: re-query the merchandising API for up to 6 already-provisioned views in the same locale and print product counts as a sanity check — this step is entirely diagnostic; it never fails the run.
The whole operation is idempotent by construction (name-keyed lookups at every step, never index- or order-dependent), and dry-run is the DEFAULT (`--yes` opts into writes) — this is the single most important UX property to preserve in the MCP tool design.

**Command-by-command value assessment (opinionated):**
- **Genuinely valuable, MCP-worthy (read-only)**: `source list`, `pricebook list`, `key list`, `view list`, `view count` (queries live product counts, useful diagnostic), `policy list`, `attribute list`, `attribute values`. All map to a single read-only tool call each or can be folded into fewer thick tools.
- **Genuinely valuable, but a MUTATION that agents should be able to trigger deliberately**: `policy enable`/`disable` (toggle-only, reversible, does not delete anything), `provision` itself in dry-run mode (simulation is safe and highly agent-appropriate — "what WOULD happen" is exactly an agent-useful read).
- **CLI-ONLY, confirmed candidates** (destructive or requiring a human `--yes` gate the way the EDS precedent treats `site delete`/`key delete`): `provision --yes` (the prior exploration's suggestion holds — irreversible bulk creation across potentially dozens of catalog views/policies should require a human at a terminal, not an agent's single tool call), `view delete`, `view prune --yes` (bulk-deletes ALL untracked `_draft` views in one pass — the blast radius scales with tenant state, not with a bounded input array, which is structurally different from EDS's bounded `paths` arrays and cannot be made safe by a `nonEmptyPaths`-style schema gate), `policy delete`. `profile`/`auth` commands are inherently CLI-only (interactive credential management, matches `eds-cli`'s `auth mint`/`auth status` precedent). `api query` (raw GraphQL escape hatch) should stay CLI-only exactly as EDS has no equivalent MCP tool for raw queries — an unconstrained query string is the opposite of a task-shaped tool.
- **Vestigial or dev-only, do not port**: `policy init` (one-time CSV scaffolding for THIS operator's own local workflow, tied to a file that doesn't exist in this repo), the entire local CSV-file-as-state-store pattern for policies (`data/vertical-policies.csv`) is a local-dev artifact specific to the reverse-engineered CLI's own workflow, not a data shape Adobe's API exposes — `aco-package`'s `provision`-equivalent tool should take vertical/attribute/value triples as tool ARGUMENTS, not read a CSV the MCP server has no business owning.

### 2. Adobe documentation — VERIFIED vs INFERRED

**VERIFIED (fetched from developer.adobe.com / experienceleague.adobe.com, current as of 2026-09-10):**
- IMS Server-to-Server: token endpoint `https://ims-na1.adobelogin.com/ims/token/v3`, POST, `grant_type=client_credentials`, `client_id`, `client_secret`, `scope` (comma-separated) in the request BODY (Adobe explicitly recommends body over query params to avoid server-log leakage). Token lifetime is **documented as exactly 86399 seconds (~24h)** — NOT an undocumented CLI observation as the brief implied; this is an official, stated figure. Adobe explicitly states **no refresh grant exists**: "You do not need a refresh token... you can always request a new access token directly using client_id/client_secret/scope."
- Adobe Commerce Optimizer's own ingestion-auth docs list the scope `commerce.aco.ingestion` as the DOCUMENTED scope for that IMS credential type — `commerce.aco.admin` does NOT appear anywhere in Adobe's public documentation searched. **This confirms the prior exploration's finding: `commerce.aco.admin` and the Studio admin GraphQL endpoint are undocumented / reverse-engineered.**
- Merchandising API (`developer.adobe.com/commerce/services/optimizer/merchandising-services/using-the-api`) documents exactly four headers: `AC-View-ID` (required), `AC-Policy-{*}` (optional, data-access filters), `AC-Price-Book-ID` (optional), and `AC-Catalog-View-Access-Token` (conditionally required — ONLY for private/protected catalog views). It does NOT document `AC-Scope-Locale` by that exact name, but a companion limitations page confirms "All queries require a specific locale to be set in the headers" — so a locale header exists and is required, matching the CLI's usage, even though the canonical header name wasn't confirmed verbatim on the fetched page.
- Restricted access keys ARE documented, but as an RSA key-pair + per-request JWT-signing mechanism (2048–8192-bit keys, public key registered in Studio, private key kept locally to sign each request, RS256 server-side verification), max 3 per catalog view / 100 per environment, ~5-minute revocation propagation. This is NOT a bare static string dropped into a header.

**INFERRED / NOT resolvable from documentation alone:**
- Whether the operator's specific tenant/catalog views are unprotected (matching what the CLI actually sends) or whether a future scope will require the RSA-JWT mechanism — this is a tenant configuration fact, not something Adobe's docs or this exploration can determine; it must be confirmed against the actual target tenant before design.
- The admin GraphQL schema itself (types, exact mutation input shapes beyond what the CLI's own queries reveal) remains entirely unconfirmed by any Adobe source — the Python CLI genuinely is the only "spec" for it, exactly as the brief states.

### 3. MCP tool design proposal

Following `eds`'s precedent (few, thick, task-shaped tools with WHEN-to-use descriptions), propose **six tools**, all confined to the Merchandising track plus read-only admin listings that carry no write risk:

1. **`aco_search_catalog`** — wraps `productSearch` (phrase/page/facets) against a given `viewId`/`locale`/optional `priceBookId`. `readOnlyHint: true, destructiveHint: false, idempotentHint: true`. This is the single highest-value agent capability: "what products match X in view Y."
2. **`aco_get_facet_values`** — wraps the facet/bucket query used by `attribute list`/`attribute values`, returning counts per value for a named attribute. Same annotations as above. Chains internally: try the facet query first; if the attribute isn't facetable, does NOT fall back to the CLI's brute-force page-sampling loop (that loop issues up to `pages` full product-list queries and is exactly the kind of unbounded, resource-heavy fallback an agent should not trigger implicitly) — instead it returns a structured "not facetable" result and lets the caller decide whether to sample explicitly via a bounded, explicit argument.
3. **`aco_list_catalog_views`** — wraps `Q_VIEWS`, with an optional filter to exclude `_draft`-suffixed entries by default (mirrors `view list`'s default). Read-only.
4. **`aco_list_price_books`** — wraps the cursor-paginated `Q_PBOOKS`, accepting/returning `scrollId` the same way EDS tools pass through `nextToken`. Read-only.
5. **`aco_list_policies`** — wraps `Q_POLICIES`. Read-only.
6. **`aco_toggle_policy`** — the one MERCHANDISING-adjacent mutation worth exposing: enable/disable a named, non-empty list of policies (never "all" implicitly). Discriminated-union hazard shape mirroring `eds_reindex`: `{ mode: "named", names: nonEmptyPolicyNames }` only — there is deliberately NO `{ mode: "all" }` branch on the MCP surface at all (unlike `eds_reindex`'s full-site branch, which IS reachable with double confirmation); `policy disable --all` stays CLI-only because "all" is tenant-state-dependent (reads a local CSV in the CLI) and its blast radius is unbounded from the MCP server's point of view. `readOnlyHint: false, destructiveHint: true, idempotentHint: true` (mirrors `eds_set_live_state`: toggling to a state already held is a no-op, confirmed by the CLI's own `pol_enabled(p) == target` early-exit).

**Explicitly CLI-only (no MCP tool)**: `provision` (any mode — even dry-run, because "what would happen" still requires resolving policy/price-book state across the whole tenant and is the CLI's most expensive, most interactive operation; unlike EDS's `site apply` this has no bounded per-call cost), `view delete`/`view prune`, `policy delete`, all `profile`/`auth` subcommands, `api query`. This is a smaller MCP surface than EDS's 9 tools, proportional to how much of ACO's real value (provisioning, policy authoring) is inherently a human-in-the-loop, tenant-wide operation rather than a bounded per-call query.

**Hazard shapes identified**: `policy disable --all` → solved by omitting the "all" branch entirely from the wire schema (stronger than EDS's double-literal-confirmation pattern, appropriate because there is no bounded-but-large version of "all" the way `eds_reindex`'s full-site branch at least operates on one already-known site). `view prune` → no MCP equivalent at all, for the same reason (unbounded, tenant-state-dependent blast radius, not expressible as a `nonEmptyPaths`-style array because the "paths" here are DISCOVERED by the operation itself, not supplied by the caller).

### 4. Testing strategy

- **Synthetic-fixture-first, no live tenant recording** — confirmed as the only viable approach; the CLI's own CSVs contain real vertical/store-view/attribute-value business data (verified but not reproduced here — see Security Constraint below) that cannot be scrubbed the way a credential can, matching the brief's framing exactly.
- **GraphQL-over-HTTP-200 error fixtures**: the TS client's test doubles need a THIRD response shape beyond "success" and "network failure" — an HTTP 200 body containing `{ data: null, errors: [{ message, extensions: { code, classification } }] }` — and tests must assert that this shape is detected independent of `response.ok`/`response.status` (which will read `true`/`200`). This is a materially different fixture shape from anything in `packages/eds/src/testing/fetch-double.ts` today (EDS has never needed a "successful transport, failed operation" double) — `aco`'s test-double helper will need its own variant, not a reuse of EDS's as-is.
- **Cross-domain end-to-end scenario**: worth building, but ONLY after the `catalog-views.csv` column-shape gap (above) is resolved, since the scenario's entire premise — "aco provisions `ac_view_id`, eds consumes it" — is not currently expressible against the committed fixture. Once resolved, the scenario should assert: `aco`'s provision-equivalent (in tests, a fixture-fed function, not a live call) writes an `ac_view_id` for a synthetic vertical/site pair, and `eds`'s `site apply`-equivalent config path can read that exact same row and produce a config referencing it — proving the fixture is genuinely shared state, not two packages each parsing their own copy coincidentally compatibly.
- **Cold-start budget**: leave the existing PROVISIONAL 250ms threshold as-is (see Current State above) unless `aco`'s actual built bundle size differs from `eds`'s by more than 20%, per the spec's own documented re-measure trigger. Do not treat re-deriving it on real CI as in scope for this change.

### 5. Risks and open questions

1. **[OPEN, needs product/design decision]** Whether the "Merchandising restricted access key" is (a) simply absent for unprotected catalog views (what the reverse-engineered CLI actually does — zero secret material sent) or (b) an RSA-JWT-per-request signing mechanism for protected views (what Adobe documents). These imply very different `TokenProvider`/client designs. Must be confirmed against the actual target tenant's catalog-view protection setting before design.md commits to a shape.
2. **Confirmed capability gap**: committing the MCP server to the Merchandising track means an agent CANNOT create/modify catalog views, create/modify/delete policies, or provision anything — all of that stays CLI-only per this exploration's own tool-design recommendation. An agent CAN search/browse an already-provisioned catalog and toggle an existing policy on/off. This is a real, not hypothetical, reachability gap: any workflow that needs "set up a new vertical's catalog view end-to-end" is unreachable from the MCP surface by design, and that trade-off should be stated explicitly in the proposal, not left implicit.
3. **`catalog-views.csv` schema gap** (see Current State) blocks the literal cross-domain hand-off described in the brief until resolved — likely an additive-columns migration (`ac_view_id`, `ac_price_book_id`, `currency`, and reconciling `site`/`store_view` naming), which is itself a small cross-cutting change to a shared `mcp-testing` fixture and its test.
4. **Rate-limit/throttle signal shape is unconfirmed beyond "HTTP-200 errors[] with optional extensions.code/classification"** — no documented Adobe rate-limit code was found for the admin GraphQL API (undocumented surface), so the TS client's throttle detection will necessarily be heuristic (message/extension pattern matching) rather than a confirmed contract, unlike EDS's crisply-specified `429`/`503+x-error` split.
5. **Admin `client_credentials` may simply not work for this scope in production**, per the CLI's own field notes — meaning `MintedTokenProvider`'s automatic path could be dead code in practice for some tenants. It should still be implemented and attempted (low cost, and it may work in other tenants/orgs), but the design should not treat manual paste as a fallback-only path — it is a primary path.
6. Could not determine the exact GraphQL type/field shapes beyond what the CLI's literal query/mutation strings reveal (no schema introspection was available in this exploration) — a design-phase decision is needed on whether to hand-write minimal TS response types (matching EDS's `types.ts` pattern) purely from these literal strings, accepting the risk that any field the CLI never queries is simply unknown.
