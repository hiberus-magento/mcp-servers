# Proposal: aco-package — `hiberus-aco` CLI and `hiberus-aco-mcp` server

## Intent

`eds-package` (change 2) proved the shared libraries against a real API with the cheapest possible auth: one static key, one HTTP surface, status-code errors. Adobe Commerce Optimizer (ACO) is the programme's third package and the first that breaks all three of those assumptions at once:

- **Two endpoints, not one** — an undocumented, reverse-engineered *admin* GraphQL surface, and a documented *Merchandising* catalog surface.
- **Two unrelated credential models** — a short-lived IMS Bearer for admin, and, for Merchandising, either **no credential at all** or an RS256 JWT signed per request. These are not variations of one scheme.
- **Errors that never appear in the HTTP status** — ACO returns `HTTP 200` with a GraphQL `errors[]` array. Status-based error handling, which is exactly what the EDS client does, is wrong here *by construction*.

This change is therefore where the programme finds out whether `mcp-core`'s credential primitives generalise beyond a static key, and whether a domain whose failures are invisible to the transport can be made safe. It is also the first consumer of `MintedTokenProvider`, which change 1 built and change 2 never used.

## Scope

### In Scope

**`packages/aco`**, scaffolded from `templates/server/` via `pnpm new-server`, with the architecture `eds` established:

- **`client/`** — the whole domain: the two endpoint shapes, header assembly, GraphQL-error classification, throttle pacing, `scrollId` pagination, response types, and the `provision` pipeline as a pure function over injected values. `client/index.ts` is its only public surface; the eslint `no-restricted-imports` boundary rule stops the adapters reaching deep paths. `client/` contains no `console.*`, no `process.exit`, no prompts, no colours, never reads `process.env` directly, and returns objects, never formatted strings.
- **`cli.ts`** — thin adapter: argument parsing, `process.env` reading, formatting, exit codes, and every CLI-only operation on the exclusion list below.
- **`mcp.ts`** — thin adapter: six `defineTool()` registrations over the same client.
- Admin-track auth wiring as a **pure consumer** of `mcp-core` (`MintedTokenProvider`, `CredentialExpiredError`, `resolveCredentialValue`, `persistCredential`).
- `auth token set` (stdin only), `auth status`, `auth mint` (CLI-only) — mirroring `eds-cli`.
- A synthetic-fixture suite under Strict TDD, a `servers.json` entry, and the README regenerated by the existing generator.

**`packages/mcp-testing`** — migrate `catalog-views.csv` to the column shape the ACO↔EDS hand-off actually needs, and migrate its test with it.

### Out of Scope

- **Any change to `mcp-core`.** Verified by reading `src/credentials/token-provider.ts`, not by trusting the exploration: `MintedTokenProvider` already has an async `mint()` hook, a required `mintTimeoutMs` (a hung IMS call fails fast rather than stalling a tool call), `skewMs` for early refresh, single-flight coalescing (two concurrent calls do not double-mint), and generation-stamped `invalidate()` (a 401 invalidates only the generation that produced it). `CredentialExpiredError` is already exported and already generic. Both are unused by `eds`. This is an exact fit for an IMS `client_credentials` token with no refresh grant. Reuse unmodified; do not fork or extend.
- **RS256 per-request JWT signing** for protected catalog views. No target catalog view is protected today, and building a signing provider for a hypothetical is speculative work. What this change owes is that the *client* not make it impossible later: header assembly takes an optional `catalogViewAccessToken` supplier, and the `access-key-invalid` failure is classified and given a remedy even though nothing currently produces it.
- Recording real API traffic against any real tenant, and any real vertical, store-view, attribute value or SKU anywhere in this repository.
- Closing the cold-start CI-measurement gap (see Approach).
- `magento-cloud` and Dockergento packages (changes 4–5).
- The local `data/vertical-policies.csv` state-store pattern from the Python CLI. It is that operator's own local workflow artifact, not a shape Adobe's API exposes. `provision` takes vertical/attribute/value triples as arguments.

## Capabilities

### New Capabilities

- `aco-client`: the ACO domain client — the admin and Merchandising endpoint shapes, the three credential models kept separate, the `HTTP 200 + errors[]` typed error hierarchy keyed off `extensions`, heuristic throttle detection and pacing, `scrollId` pagination, the six admin mutations, the four-step idempotent `provision` pipeline, and the `client/` purity constraints.
- `aco-cli`: the `hiberus-aco` binary — command surface, stdin-only token intake, dry-run-by-default `provision`, and the CLI-only operations excluded from MCP.
- `aco-mcp`: the `hiberus-aco-mcp` server — the six-tool task-shaped surface, its annotations, and the deliberate absence of an "all" branch on the wire schema.

### Modified Capabilities

- `mcp-conformance`: the "Shared Synthetic Catalog-Views Fixture" requirement gains the column shape the cross-domain hand-off requires (`ac_view_id`, `ac_price_book_id`, `currency`), so the fixture is genuinely shared state rather than two packages parsing coincidentally-compatible copies.

## Approach

### Three credentials, kept apart on purpose

Conflating these is the single easiest way to build the wrong client. They share nothing — not a header, not a lifetime, not a failure mode.

| # | Credential | Header | Track | Lifetime |
|---|---|---|---|---|
| 1 | IMS Bearer (+ `x-api-key`) | `Authorization: Bearer …`, `x-api-key` | ACO **admin** GraphQL | ~24 h, no refresh grant |
| 2 | RS256 JWT, signed per request | `AC-Catalog-View-Access-Token` | ACO **Merchandising**, *protected views only* | Per request; the underlying key pair expires |
| 3 | Static API key | `X-Auth-Token` | **EDS** — not ACO at all | Until rotated |

**Merchandising authentication is not required by default.** Adobe states this explicitly; only a catalog view with *Catalog Protection* enabled needs credential #2. The Python CLI sends no credential to Merchandising because it creates every view with protection disabled — that is correct behaviour, not an omission. A "restricted access key" is an RSA **key pair**, never a pasteable string.

### The MCP server rides the Merchandising track

Decided, not reopened. Two reasons: catalog reads are what an agent actually needs, and the admin Bearer expires in hours — an MCP server that dies mid-session waiting on a human to paste a token from a browser devtools panel is not a server. Merchandising needs `AC-View-ID` (required), optionally `AC-Price-Book-ID` and `AC-Policy-{*}`, and — for unprotected views — no secret material whatsoever. The admin Bearer stays confined to the CLI, where a human is already present.

### The error model: never trust the status code

ACO wraps operational failure as `HTTP 200` with a top-level `errors[]` array. The typed hierarchy keys off `errors[].extensions`, not the status:

| Signal in `errors[].extensions` | Class | Remedy |
|---|---|---|
| `x-commerce-exception: "access-key-invalid"` | `CatalogViewAccessError` | Register or rotate a restricted access key in Studio for this view |
| `classification`/`code` matching `permission\|scope\|unauthor\|forbidden` | `AdminScopeError` | Named below — two remedies, not one |
| `classification`/`code` looking throttle-shaped | `AcoThrottledError` | Backoff; see pacing |
| anything else | `AcoOperationError` carrying `message` + `extensions` verbatim | Surface Adobe's own text |

Transport-level failure (`fetch` rejection, a 5xx that never forms a GraphQL envelope) stays a separate class with a "check your region/tenant" remedy, exactly as the Python CLI distinguishes them.

**A test must prove a `200`-with-`errors[]` is not treated as success.** This needs a third test-double shape that `packages/eds/src/testing/fetch-double.ts` has never had — EDS never needed "successful transport, failed operation". The scope/permission substring match is a *best-effort classifier*, not a contract: Adobe publishes no structured code for it, and the client must say so where the classifier lives.

### Admin auth: mint first, paste is equally primary

1. Attempt `MintedTokenProvider` wrapping a form-urlencoded POST to `https://ims-na1.adobelogin.com/ims/token/v3` (`grant_type=client_credentials`), if a client id/secret is configured.
2. **That grant may simply not work.** The scope `commerce.aco.admin` appears nowhere in Adobe's public documentation, and the Python CLI's own field notes record it failing in the operator's tenant. When it fails on scope, the error is a `MissingCredentialError` naming *both* exits — re-attempt the mint, or paste a Studio session Bearer — never an opaque network error.
3. `hiberus-aco auth token set` reads a Bearer from stdin (no `--token` flag exists; an argument lands in shell history) and persists to `$XDG_CONFIG_HOME/hiberus/aco.json` at `0600`.
4. A pasted Bearer's `created_at`/`expires_in` claims are decoded **without signature verification**, purely to compute expiry, and `CredentialExpiredError` is thrown before a stale Bearer is ever sent.

Manual paste is a **primary path**, not a fallback. Both paths ship.

### Pacing: no fixed sleeps

The Python CLI has no client-side throttle — only `time.sleep(0.3)`/`sleep(0.4)` courtesy delays inside `provision` and `view prune`, absent entirely from read paths. Those are not ported. The client reuses the `TokenBucketRateLimiter` pattern from `packages/eds/src/client/rate-limiter.ts`, sized conservatively for the mutation fan-out. **Detection differs structurally from EDS**: `mapThrottle` there is entirely status-code-driven, and here no status code ever carries the signal. Throttle detection parses `errors[].extensions`, and since Adobe documents no throttle code for this surface, it is explicitly heuristic — recorded as such next to the code, and the retry budget is bounded so a misclassification cannot become a retry storm.

### Pagination and mutations

`scrollId` is cursor-style and confirmed on **`priceBooks` only** — passed through the same way EDS passes `nextToken`. Every ACO write reduces to one of six admin mutations: `createChannel`/`updateChannel`/`deleteChannel`, `createPolicy`/`updatePolicy`/`deletePolicy`. There are no others.

### `provision`: four idempotent steps, dry-run by default, CLI-only

1. **Validate attribute** (skippable) — query one Merchandising facet per vertical and abort *before writing anything* if a vertical's expected value matches zero products, so empty catalog views are never created.
2. **Policies** — create by name if absent, otherwise reuse the existing `policyId`. Idempotent by name lookup, never by comparing filter contents.
3. **Catalog views** — resolve the price-book family by walking `parentIds`, then `createChannel` followed by a second `updateChannel` to attach `defaultPriceBookId` (two calls; the create input does not accept it), or `updateChannel` alone when only `policyIds` differ. A correct existing view is a no-op.
4. **Verify** — re-query product counts as a diagnostic. Never fails the run.

Idempotent by construction: every step is name-keyed, never index- or order-dependent. **Dry-run is the default; `--yes` opts into writes.** That is the single most important UX property to preserve, and it is preserved by keeping `provision` off the MCP surface entirely — including dry-run, because "what would happen" still resolves policy and price-book state across the whole tenant and has no bounded per-call cost.

### MCP surface: six thick, task-shaped tools

| Tool | Arguments | Chains internally | Returns | `readOnly` / `destructive` / `idempotent` |
|---|---|---|---|---|
| `aco_search_catalog` | `{ viewId, locale, phrase, pageSize?, currentPage?, priceBookId? }` | Merchandising `productSearch` | `{ totalCount, items[], facets[] }` | `true / false / true` |
| `aco_get_facet_values` | `{ viewId, locale, attribute, priceBookId? }` | facet/bucket query only | `{ facetable: true, values: [{ value, count }] }` **or** `{ facetable: false, reason }` | `true / false / true` |
| `aco_list_catalog_views` | `{ includeDrafts? }` (default `false`) | admin `channels` | `{ views: [{ channelId, name, locales[], defaultPriceBookId, policyIds[], protectionEnabled }] }` | `true / false / true` |
| `aco_list_price_books` | `{ size?, searchTerm?, scrollId? }` | admin `priceBooks` | `{ items: [{ id, name, currency, level, parentIds[] }], scrollId? }` | `true / false / true` |
| `aco_list_policies` | `{}` | admin `policies` | `{ policies: [{ policyId, name, mandatory, actions[] }] }` | `true / false / true` |
| `aco_toggle_policy` | `{ mode: "named", names: string[] (min 1), enabled: boolean }` | `updatePolicy` per name | `{ results: [{ name, previous, current, changed }] }` | `false / true / true` |

`aco_get_facet_values` deliberately **does not** fall back to the CLI's brute-force page-sampling loop when an attribute is not facetable. That loop issues up to *pages* full product-list queries; an agent must not trigger it implicitly. It returns a structured "not facetable" result and lets the caller ask explicitly.

`aco_toggle_policy` is `idempotentHint: true` because toggling to a state already held is a no-op — the CLI's own `pol_enabled(p) == target` early-exit proves it. It has **no `{ mode: "all" }` branch on the wire schema at all.** This is stronger than `eds_reindex`'s double-confirmation gate, and deliberately so.

**CLI-only, with reasons:**

| Operation | Why no MCP tool |
|---|---|
| `provision` (**including dry-run**) | Tenant-wide, unbounded per-call cost, irreversible in `--yes` mode; needs a human at a terminal |
| `policy disable --all` | Blast radius is **discovered from tenant state**, not bounded by arguments — a confirmation gate cannot make it safe |
| `view prune` | Same: bulk-deletes every untracked `_draft` view; the "paths" are discovered by the operation itself, so no `nonEmptyPaths`-style schema gate applies |
| `view delete`, `policy delete` | Irreversible deletion of provisioned state |
| `auth` / `profile` | Interactive credential management, matching `eds-cli` precedent |
| `api query` | An unconstrained GraphQL string is the exact opposite of a task-shaped tool |
| `policy init` | Vestigial: scaffolds a local CSV that does not exist in this repository |

### The reachability gap, stated plainly

With the MCP server on Merchandising, an agent **can** search and browse a provisioned catalog, inspect views, price books and policies, and toggle an existing policy. An agent **cannot** provision anything, nor create, edit or delete a catalog view or a policy. Every mutation-heavy operation ACO offers stays CLI-only.

**This is the right trade, and it is a real loss.** The loss: "set up a new vertical end to end" is unreachable from the MCP surface. Why it is still right: those operations are tenant-wide, their blast radius is discovered rather than declared, and the credential they need dies in hours. A surface that exposed them would be a surface an agent could use to silently restructure a customer's catalog on a token that expires before anyone notices. Six reachable, cheap, bounded tools beat nine where three are landmines. If provisioning must become agent-reachable later, the honest route is a bounded, argument-declared `aco_provision_view` for a *single* `(vertical, view)` pair — a different tool with a different blast radius, not a flag on this one.

### `catalog-views.csv`: migrate now, additively

The committed fixture is `vertical,site,locale,view_code`. It cannot carry the hand-off, because `aco provision` produces an `ac_view_id` and an `ac_price_book_id` and `eds site apply` consumes them. Migration is **additive** — no existing column is renamed or dropped, so no existing consumer breaks:

```
vertical,site,locale,view_code,ac_view_id,ac_price_book_id,currency
```

`site` is kept over the Python CLI's `store_view` (it is this repository's word and EDS's word), and `view_code` is kept alongside `ac_view_id` (the human-readable view name and the tenant-assigned identifier the `AC-View-ID` header needs are genuinely two things). `catalog-views.test.ts` migrates with it and gains column-shape assertions. Every value stays synthetic, imported from `synthetic-identifiers.ts`.

### Cold start: leave the provisional 250 ms

`COLD_START_BUDGET_MS = 250` is a local-derived p95 (`ceil(46.6 × 1.75)`, rounded up), explicitly marked PROVISIONAL, with a documented re-measure trigger: real CI numbers become available, **or** bundle shape moves >20%. This change does **not** close it. Closing it requires a `workflow_dispatch` CI job — orthogonal infrastructure, not ACO domain work, and doing it here would bury it in an unrelated diff. What this change does owe is honesty about the trigger: `aco`'s bundle is measured, and if it differs from `eds`'s by more than 20%, the spec's own trigger fires and a new local-provisional number is recorded the same disclosed way.

### Testing: synthetic-fixture-first

Zero recorded traffic. The audited Python source carries real vertical names, a real store-view naming scheme and at least one real SKU, and this repository is public — business data cannot be scrubbed the way a credential can. Fixtures are schema-accurate, derived from the CLI's literal query strings and Adobe's documented Merchandising shapes, and every identifier comes from `synthetic-identifiers.ts`. `scripts/audit-synthetic-identifiers.mjs` already guards this with a hashed denylist matching spaced, hyphenated and concatenated spellings — it caught a leak in this change's own exploration. Strict TDD: every behaviour above starts as a failing test.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| **The admin `client_credentials` grant may be genuinely non-functional for `commerce.aco.admin`** in production tenants, per the Python CLI's own field notes | High | Manual Studio Bearer paste is a **primary** path, shipped and documented as such — not a fallback. The mint attempt is cheap and may work in other orgs, so both ship. A scope failure produces a remedy naming both exits. |
| **The admin GraphQL surface is undocumented and reverse-engineered** — `commerce.aco.admin` appears nowhere in Adobe's public docs, and no schema introspection was available. Schema fidelity is bounded by the Python source | High (certain) | Hand-write minimal response types from the CLI's literal query strings, exactly as `eds/client/types.ts` does. **Consequence recorded in the spec**: any field the CLI never queries is simply unknown, so response parsing is tolerant — unknown fields pass through, missing optional fields do not throw. A field we did not anticipate must not crash a tool call. |
| **No documented throttle signal for the admin surface** — detection is heuristic pattern-matching on `errors[].extensions` | Medium | Bounded retry budget so misclassification cannot storm; the heuristic is labelled at its definition; a conservative token bucket does the real pacing rather than relying on detection. |
| **Real customer identifiers exist throughout the audited Python source and this repository is public** | High | No Python source is copied. Every fixture, example and sample value imports from `synthetic-identifiers.ts`. `scripts/audit-synthetic-identifiers.mjs` runs in CI with a hashed denylist matching spaced, hyphenated and concatenated spellings; secret scanning already blocks credentials. |
| **`200`-with-`errors[]` silently read as success** — the single most consequential difference from the EDS client | Medium | A test asserts a `200` body carrying `errors[]` is never treated as success, and the `response.ok`/`status` value is asserted to be `true`/`200` in that same test so the trap is visible in the test itself. |
| **Migrating a shared `mcp-testing` fixture affects `eds`** | Medium | The migration is strictly additive — no column renamed or removed — so every existing consumer keeps working; the existing test is extended, not replaced, and `eds`'s suite must stay green as the proof. |
| **Merchandising protection could be enabled on a target view later**, requiring RS256 per-request signing this change does not build | Low | Header assembly takes an optional access-token supplier and `access-key-invalid` is already classified with a remedy, so enabling protection produces an actionable error rather than a mystery, and adding a signing provider is additive. |
| **Cold-start budget stays provisional and local-derived** | Low | The provisional status and re-measure trigger are already recorded in the spec and in `cold-start.ts`; this change measures `aco`'s bundle against the >20% trigger and records the result honestly rather than inheriting silence. |

## Rollback Plan

All work lands on a branch. `packages/aco` is new and nothing depends on it, so until publish, rollback is abandoning the branch.

Two shared touchpoints need care:

- **`catalog-views.csv`** — the migration is additive, so reverting the single commit restores the previous shape exactly. If `eds` has by then started reading a new column, revert that consumer first; the column order in the header is what the test asserts, so a partial revert fails loudly rather than silently mis-parsing.
- **`servers.json` / `README.md`** — revert the entry and re-run the generator. The README is never hand-edited, so it cannot drift.

**If `@hiberus-magento/aco` has already been published**, rollback is *not* unpublish-and-republish: npm never allows reusing a version number. `npm deprecate` the bad version with a message pointing at the fix and ship a patch. Publishing is sequenced last, after every gate is green, precisely so this branch is rarely taken.
