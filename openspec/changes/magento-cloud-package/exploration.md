The fork remains a behavioral reference only.

### Current State — verified against the REAL installed CLI, not assumed

The `magento-cloud` CLI is installed and has an authenticated session on this dev machine (`~/.magento-cloud/{state.json,ssh/,.session/,cache/}` exist with live cache entries — not opened by value, per the security constraint). **This exploration's toolset had no shell-execution capability** (no Bash tool was available to this sub-agent), so `magento-cloud --version` / `magento-cloud list --format=json` could not literally be run. Instead, the installed binary (`~/.magento-cloud/bin/magento-cloud`, 6.4 MB) was read structurally: it is a bundled PHP/Symfony-Console application (`Platformsh\\Cli\\...` namespaces throughout — this is Adobe's public white-label of the Platform.sh CLI, `github_repo: magento/magento-cloud-cli`, confirmed from the binary's own embedded config block), so its exact command surface, option definitions, and even config defaults were extracted directly via pattern search over the real binary — this is real evidence, not documentation-guessing, and is presented as such (not a network capture, no live output was ever pasted).

**Verified config block from the binary itself** (public, non-secret — this is Adobe's shipped default config, identical to what's in the public `magento/magento-cloud-cli` repo):

### Full read-only command surface — extracted from real `->setName(...)` registrations (192 total commands found; read-only-relevant subset below)

Confirmed **no bare `tunnel` subcommand exists** — only `tunnel:list`, `tunnel:open`, `tunnel:close`, `tunnel:info`, `tunnel:single`, exactly matching decision #1253's finding that `mcp-core`'s exact-token `FORBIDDEN_TOKENS` check doesn't (and structurally can't) catch these, which is fine because nothing is registered unless the domain package deliberately does so.

- `activity:list`, `activity:log`, `activity:get` — deploy/activity history, a real substitute for "why is this broken" that needs no SSH.
- `variable:list`, `variable:get` — **the CLI itself already redacts `is_sensitive` variable values** (`variable:list`'s own code: `if (!$variable->hasProperty('value', false) && $variable->is_sensitive) { row['value'] = machineReadable ? ### Machine-readable output — corrected finding, contradicts the task's own `--format=json` assumption

**The installed CLI has NO JSON output format at all.** Read directly from `Platformsh\\Cli\\Service\\Table::configureInput()` and `Table::render()`: the `--format` option's own description is `'The output format: table, csv, tsv, or plain'`, with a `switch` over exactly `csv | tsv | plain | table` and a thrown `InvalidArgumentException` for anything else (message literally lists those four). `PropertyFormatter` (used by `environment:info`/`project:info`/`subscription:info`'s single-property mode) adds no format option beyond `--date-fmt`. There is no JSON path anywhere in the console-output layer.

**`tsv` is the correct machine-parseable choice**, not a scrape-human-text trap: `renderCsv($rows, $header, "\t")` delegates to a real `Csv` formatter class (not naive tab-joining), so embedded tabs/newlines in values are properly quoted/escaped. `Table::formatIsMachineReadable()` returns `true` for `csv`, `tsv`, AND `plain` — and commands check this flag to suppress human narration lines (e.g. `variable:list`'s "Project-level variables on the project X:" banner) when a machine format is selected, so stdout stays clean for parsing. **Recommendation: always pass `--format=tsv` on every list/table-shaped subcommand**, and write a small internal TSV-row parser (header row + tab-split data rows) in the wrapper — this is the "structured output" path, and it is NOT the human-text-scraping trap the task worried about, because the CLI's own TSV renderer is a real, escaped serialization, just not JSON.

### `db:sql` — exact mechanism, read directly from `Platformsh\\Cli\\Command\\Db\\DbSqlCommand`

- The command signature is `db:sql [query] [--raw] [--schema=X] --project --environment --app` — **`query` is an OPTIONAL positional argument**. If omitted, the CLI opens an **interactive remote SQL console** over SSH with a requested TTY (`$host->setExtraSshOptions(['RequestTTY yes'])` when not `--raw` and stdin is a terminal) — this would hang indefinitely if ever invoked without a query. **The wrapper's zod schema MUST make `query` mandatory (never optional), so this shape can never be constructed.**
- With a query present, the CLI builds `mysql --no-auto-rehash <conn-args> --execute <shellEscapedQuery>` (or `psql -c` for Postgres) and runs it **over its own internal SSH connection** — confirmed exactly: `return $host->runCommandDirect($sqlCommand);` where `$sqlCommand` embeds `OsUtil::escapePosixShellArg($query)`. **This is the concrete confirmation of the user's framing: we never construct or invoke `ssh` ourselves; the CLI does that internally as its own business, and its own escaping (not ours) protects the SSH-hop shell boundary.** Our local `execFile` call passes `query` as a single argv element to the `magento-cloud` binary — Node's `execFile` bypasses any local shell entirely, so local injection is structurally impossible regardless of query content.
- **No native LIMIT, row cap, or byte cap exists in the CLI** — `--raw` only controls tabular-vs-batch mysql output mode, not any bound. The exact mechanism this package must own:
  1. Reject anything but a single statement of `SELECT`/`SHOW`/`DESCRIBE`/`DESC`/`EXPLAIN` (regex/tokenizer over the leading verb; reject any additional top-level `;`-separated statement).
  2. Reject `SELECT *` and `SELECT DISTINCT *` (and, as a documented residual gap for `sdd-design` to close or accept, a qualified `t.*` can still slip a naive regex — note this explicitly rather than silently under-covering it, and flag that a real SQL parser dependency would fight the packages' `dependencies: {}` single-file-bundle constraint).
  3. Reject `INTO OUTFILE`/`INTO DUMPFILE`/`LOAD_FILE(` — a real MySQL exfiltration/file-read path the fork's validator (and the task's own framing) didn't mention; this is a genuine addition worth carrying into the design.
  4. For `SELECT` statements only (not `SHOW`/`DESCRIBE`/`EXPLAIN`, which don't take a meaningful `LIMIT`): parse a trailing `LIMIT n[,m]`/`LIMIT n OFFSET m`; if present and `n` exceeds the configured row cap, **reject** (not silently clamp — clamping hides a caller's wrong assumption); if absent, **append** `LIMIT <rowCap>` to the query text before it ever reaches `buildArgv`.
  5. Pass `--raw` to get `mysql --batch --raw` mode, which is tab-separated and unquoted — clean for our own parsing.
  6. Combine with `mcp-core`'s existing `maxOutputBytes` as a second, independent safety net (see gap below — this only works once the env-passing gap is fixed).
  - This makes the injected `LIMIT` clause itself the row cap (bounding rows at the SQL engine, before any output exists), and `maxOutputBytes` the byte cap — two independent, complementary limits, exactly what the user asked for.

### `mcp-core`'s allowlisted executor as first real consumer — two genuine, concrete gaps found (reported LOUDLY, with in-domain fixes preferred per the user's standing decision)

**Gap 1 — `runAllowlisted` gives the child process ZERO environment variables, unconditionally, with no override point.** Read directly: `run-allowlisted.ts` hardcodes `env: {}` inside the `execFile` options object; `CommandSpec` (in `command-spec.ts`) has no `env` field at all; there is no hook for a caller to influence it. Node's `child_process` `env` option, when provided, **replaces** `process.env` entirely — it does not merge. This means `magento-cloud` would run with no `MAGENTO_CLOUD_CLI_TOKEN` (so it can never authenticate non-interactively), no `HOME` (so it likely can't even find `~/.magento-cloud`'s config/cache/session directory), and no `PATH` (needed to resolve `ssh`/`mysql` locally before the CLI's own internal SSH hop). **This is the same pattern as three prior near-misses** (a stdout guard nothing called, an identifier audit scanning the wrong files, a secret scanner never fed its real format): `exec.test.ts` and `run-allowlisted.timeout.test.ts` only ever exercise `/bin/true`, `/bin/sleep`, `/bin/echo`, `/usr/bin/git status` — binaries that need zero environment to run. `env: {}` has never been exercised against a real authenticated external CLI, because no real one existed until now.
  - **Preferred in-domain fix** (no `mcp-core` change, consistent with the user's standing decision to keep domain knowledge — and here, domain *capability* needs — inside the domain package): `CommandAllowlist.register()`, `resolve()`, and `validateArgv()` are fully reusable unchanged (they never touch env). Only the actual spawn call needs a package-local sibling to `runAllowlisted` (e.g. `packages/magento-cloud/src/exec/run-magento-cloud.ts`) that mirrors its exact M4 safety invariants (`shell: false`, `stdio: 'pipe'`, `timeout`, `maxBuffer`, `killSignal: 'SIGKILL'` — asserted by the package's own tests mirroring `exec.test.ts`/`run-allowlisted.timeout.test.ts`) but supplies an explicit, minimal env map: `{ MAGENTO_CLOUD_CLI_TOKEN: token, HOME: process.env.HOME, PATH: process.env.PATH }` — never `process.env` wholesale, preserving the original constraint's spirit.
  - **Alternative, flagged but not assumed**: an additive, non-breaking `CommandSpec.env?: Readonly<Record<string,string>>` field merged explicitly inside `runAllowlisted` (never wholesale `process.env`) would fix this once for every future domain package that needs any authenticated external CLI, not just this one — this is a structural capability gap, not domain knowledge, so it sits in a genuinely different category from the `FORBIDDEN_TOKENS`/`tunnel` question the user already settled. This exploration does not assume this change is wanted; it is named here as an explicit decision point for the user/orchestrator, defaulting to the in-domain wrapper for planning purposes.

**Gap 2 — smaller, secondary — `timedOut` conflates a real timeout with a `maxOutputBytes` (maxBuffer) overflow.** `runAllowlisted` computes `timedOut: Boolean(error?.killed && error.signal === "SIGKILL")`. Node's `execFile` also kills the child with the configured `killSignal` (here `SIGKILL`) when `maxBuffer` is exceeded, setting the same `error.killed`/`error.signal` shape as a real timeout — so a `db:sql` call that hits the byte cap is indistinguishable from one that hit the wall-clock timeout by `CommandResult.timedOut` alone. In-domain mitigation: phrase the `db:sql` tool's timeout-path error message to cover both causes ("query exceeded the configured time or output budget — narrow the WHERE clause or LIMIT further") rather than asserting a single wrong cause; no `mcp-core` change required, but worth naming so `sdd-design` doesn't silently assume `timedOut` means only "slow query."

### Authentication — fail-fast confirmed by reading the real login path, not assumed

Read `Api::isLoggedIn()` (`return session.accessToken || session.refreshToken || config.api_token`), `getOauth2Plugin()` (`throw new \\RuntimeException('Not logged in')` when unauthenticated), and the `login(LoginRequiredEvent $event)` handler: it only offers the interactive browser-login confirmation **when `$this->input->isInteractive()` is true** (Symfony Console's own TTY check on stdin). Since `mcp-core`'s `runAllowlisted` always uses `stdio: 'pipe'` (never `'inherit'`), the spawned `magento-cloud` process never has a controlling TTY, so `isInteractive()` is always `false` for us — the interactive-login branch is structurally unreachable, and the handler falls straight to `throw new LoginRequiredException()` with a message built from `getNonInteractiveAuthHelp()`, which literally says: *"To authenticate non-interactively, configure an API token using the MAGENTO_CLOUD_CLI_TOKEN environment variable."* **This is a concrete, verified guarantee that the CLI fails fast with an actionable message rather than hanging on a prompt when run under `execFile`+pipe — exactly the required behavior, achieved for free by `mcp-core`'s existing stdio design, once Gap 1 (env passing) is fixed so the token can actually reach the child.**

### `TokenProvider` — is it involved? Yes, but repurposed, not reused as-is for HTTP

`mcp-core`'s `TokenProvider`/`StaticTokenProvider`/`MintedTokenProvider` (`credentials/token-provider.ts`) are designed to hand a bearer string to an HTTP client (as `eds`/`aco` do). `magento-cloud` has no HTTP client of its own — authentication is entirely the CLI's business once it has `MAGENTO_CLOUD_CLI_TOKEN` in its environment. The reusable part is still real: `StaticTokenProvider`'s "resolve once, throw a `MissingCredentialError` with a domain-specific `Remedy` on failure" contract, and `mcp-core`'s `resolveCredentialValue({domain, envVar})` env>config-file precedence helper (exactly as `eds/src/credential-provider.ts` wires it), map cleanly onto **resolving the token value in our own process**, which we then forward as one entry in the minimal child-env map from Gap 1's fix — a different consumer (child-process env injection) of the same resolved value, not a different resolution mechanism.

### External binary dependency

`servers.json`'s `requires.binaries` currently only ever lists a package's own bin (`hiberus-eds`, `hiberus-aco`) — confirmed by reading the file directly. `schema/servers.schema.json`'s `binaries` field is a bare `string[]`, so adding a second, third-party entry (`"magento-cloud"`) alongside the package's own bin needs **no schema change** — this is new precedent in the manifest's *data*, not its *shape*. The harder, still-open question this exploration flags explicitly: **how do tests run without a real `magento-cloud` install or a real project** — since `mcp-core`'s own exec tests mock `node:child_process` for unit-level coverage (`exec.test.ts`) and only use trivial, universally-present binaries (`/bin/echo`, `/bin/sleep`) for the one real-process integration test. This package will need the same two-tier strategy: (1) unit tests that mock `execFile` entirely and assert exact `argv`/`env` shape (covers the LIMIT-injection, forbidden-token, and env-map logic with zero real dependency), plus (2) a small number of real-process tests using a **package-local, checked-in fake `magento-cloud` shell script** (mirroring `mcp-core`'s pattern of using real trivial binaries, but here a fake executable script that echoes canned TSV/error output for known argv shapes) so CI never needs a live account, a real project, or network access — this fake-binary strategy is the concrete answer to "how do tests run without a real install," and should be designed in `sdd-design`, not invented ad hoc in tasks.

### Conformance suite

`describeConformance()`'s `shellOutProbe`/`readOnlyIntrospections` options already exist (added when the shared suite was amended, per its own doc comments) but have never had a real caller: `eds`/`aco` both explicitly pass no `shellOutProbe` (confirmed by reading both `mcp.conformance.test.ts` files). `magento-cloud` will be the **first real exercise** of both: `shellOutProbe` against one genuine `execFile`-based read-only tool (proving the fd-1 isolation holds for a real child process, not the synthetic `read-echo` fixture), and `readOnlyIntrospections` against `CommandAllowlist.listCommandKeys()`'s real output for a read-only-hinted tool — this is exactly the scenario the mechanism's doc comments describe but that no package has yet triggered for real.

### Ready for Proposal

Yes, with one explicit pre-`sdd-propose` decision point to surface to the user: **how to resolve Gap 1 (env-passing)** — in-domain spawn wrapper (default recommendation, zero `mcp-core` change) vs. a small additive `CommandSpec.env` field in `mcp-core` (fixes it once for every future exec-based domain package, but is a `mcp-core` change the user has been protective of). Everything else in this pass — the read-only command set, the `db:sql` LIMIT/no-`SELECT *`/row-cap/byte-cap mechanism, the TSV-not-JSON output strategy, the fail-fast auth guarantee, and the fake-binary test strategy — is evidence-grounded and ready to carry into `sdd-propose` without further clarification.

## Key Learnings

1. The installed `magento-cloud` CLI is Adobe's public white-label of the Platform.sh CLI (`github_repo: magento/magento-cloud-cli`) and supports NO JSON output format at all — only `table`, `csv`, `tsv`, `plain` — contradicting the common assumption that a modern CLI exposes `--format=json`; `tsv` is the correct machine-parseable choice because its `Csv` formatter properly escapes embedded tabs/newlines.
2. `db:sql`'s `query` argument is optional at the CLI level and opens a hanging interactive remote SQL console with a requested TTY when omitted — the wrapper's schema must make it mandatory to prevent ever constructing that shape.
3. `mcp-core`'s `runAllowlisted` hardcodes `env: {}` for every spawned child with no override point, meaning any real authenticated external CLI (needing a token, `HOME`, or `PATH`) cannot function through it unmodified — a genuine, previously-unexercised gap, distinct from the already-settled `FORBIDDEN_TOKENS` question, best fixed in-domain via a package-local spawn wrapper that mirrors `runAllowlisted`'s exact safety invariants.
4. The CLI's own non-interactive-login guard (`Symfony\\Console\\Input::isInteractive()`, false whenever stdin isn't a TTY) combined with `mcp-core`'s existing `stdio: 'pipe'` design means the CLI already fails fast with an actionable `MAGENTO_CLOUD_CLI_TOKEN`-naming error instead of hanging on a prompt — this guarantee falls out of the existing architecture for free, once the env-passing gap is fixed.
5. `runAllowlisted`'s `timedOut` flag is ambiguous between a real wall-clock timeout and a `maxOutputBytes` (maxBuffer) overflow, because Node's `execFile` kills the child with the same configured `killSignal` in both cases — relevant specifically to `db:sql`'s byte-cap enforcement.
