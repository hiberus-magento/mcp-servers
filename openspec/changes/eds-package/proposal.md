# Proposal: eds-package — `hiberus-eds` CLI and `hiberus-eds-mcp` server

## Intent

`mcp-servers-bootstrap` shipped the workspace, the packaging gate, `mcp-core`'s six primitives and a CI-blocking conformance suite — with no domain logic. This change is the programme's first real domain package: an Edge Delivery Services (EDS) Admin API client exposed as a CLI and as an MCP server. EDS is chosen second because it has the cheapest auth of the four domains (a static API key) and because it is the first package that proves the shared libraries against a real API rather than a template. It also pays down the one gate change 1 deliberately deferred — the cold-start time budget — by measuring it instead of guessing it.

EDS is also the first package that is a **pure HTTPS domain**: it shells out to nothing. That exposes a real gap in the shared conformance suite, which this change fixes properly rather than working around.

## Scope

### In Scope

**`packages/eds`**, scaffolded from `templates/server/` via `pnpm new-server`, with the programme's decided architecture:

- **`client/`** — the whole domain: auth, HTTP, request pacing, retry/backoff policy, types, pagination, job polling, error mapping. `client/index.ts` is its only public surface; the eslint `no-restricted-imports` boundary rule (workspace-scaffolding, "Client-Boundary Import Rule") stops the adapters reaching deep paths. `client/` contains no `console.*`, no `process.exit`, no prompts, no colors, never reads `process.env` directly (values are injected), and returns objects, never formatted strings.
- **`cli.ts`** — thin adapter: argument parsing, `process.env` reading, formatting, exit codes.
- **`mcp.ts`** — thin adapter: `defineTool()` registrations over the same client.
- Auth wiring as a **pure consumer** of `mcp-core` (`StaticTokenProvider`, `resolveCredentialValue`, `persistCredential`): `EDS_TOKEN` → `$XDG_CONFIG_HOME/hiberus/eds.json` at mode `0600` → `MissingCredentialError` carrying a remedy.
- `auth token set` (stdin only), `auth mint` (CLI-only), `auth status` (probe-based, never echoes a key value).
- A synthetic-fixture test suite under Strict TDD, and a `servers.json` entry with the README regenerated by the existing generator.

**`packages/mcp-testing`** — a domain-independent stdout-purity probe plus a new cold-start time budget (see Approach).

### Out of Scope

- Any change to `mcp-core`. The exploration confirmed its credential primitives already satisfy EDS's static-key model exactly; reuse them unmodified, do not fork or extend.
- Recording real API traffic against any real tenant, and any real organization, site or domain identifier anywhere in this repository.
- Everything on the CLI-only exclusion list below is out of the **MCP** surface, not out of the package.
- Out of the package entirely (out of domain, per the exploration): `spec build`, `dns *`, `config from-file`, `config from-db` — all specific to one customer's bespoke site model or coupled to a separate Commerce CLI, so porting them would smuggle unrelated domain logic and unrelated `execFile` allowlist entries into a generic package. Also dropped: `site browser` (writes an executable payload for devtools paste, and duplicates a session-cookie auth path the transport policy steers away from), the macOS Keychain fallback (forbidden native dependency), and the `EDS_AUTH_HEADER` custom-header override (vestigial, not corroborated as a generic requirement).
- ACO, magento-cloud and Dockergento packages (changes 3–5).

## Capabilities

### New Capabilities

- `eds-client`: the EDS Admin API domain client — auth header shape, request pacing against the documented limits, `429`-vs-`503` throttle disambiguation, job envelope and 2xx-success handling, pagination, tolerant response shapes, GET-before-write existence checks, and the no-side-effects `client/` purity constraints.
- `eds-cli`: the `hiberus-eds` binary — command surface, stdin-only token intake, `auth mint`, `auth status`, exit codes, and the CLI-only operations excluded from MCP.
- `eds-mcp`: the `hiberus-eds-mcp` server — the nine-tool task-shaped surface, its annotations, and the two hazard gates.

### Modified Capabilities

- `mcp-conformance`: **(a)** the "Stdout Purity Assertion" requirement gains a **domain-independent** fd-1 contamination probe, so a package with no `execFile`-based tool no longer has to ship a decorative one; **(b)** a new "Cold-Start Time Budget" requirement, measured in this change.

## Approach

### Auth: paste-then-mint

Minting a key requires an existing `admin`-scoped key, and Adobe's own UI is the only source of the first one. So the flow is sequenced:

1. The operator obtains an initial `admin`-scoped key from Adobe's admin/Sidekick UI — outside this package's control.
2. `echo "$KEY" | hiberus-eds auth token set` — **stdin only**. No `--token` flag exists anywhere, because a token passed as an argument lands in shell history.
3. Once bootstrapped, `hiberus-eds auth mint --scope <org|site> --roles <...>` calls `POST /config/{org}/sites/{site}/apiKeys.json` to mint narrower-scoped keys for day-to-day use, so the powerful bootstrap key is not reused everywhere.

**The minted value is returned exactly once and is never retrievable afterwards.** The CLI must make that unmissable: print the value on its own, state plainly that it cannot be recovered, and tell the operator what to do with it before it scrolls away. `auth mint` stays CLI-only — credential minting is high blast radius and org-structural.

`auth status` probes two or three cheap read endpoints and reports the status per probe with a plain-English verdict, never echoing the key. `mcp-core`'s redaction masks `authorization`/`token` pairs as defense in depth.

### Documented API behavior — corrections carried forward

The prior change's exploration recorded several EDS behaviors as undocumented folklore. This exploration verified against `https://www.aem.live/docs/limits` and `https://www.aem.live/docs/admin.html` that most are **documented verbatim**. The client is built on the documented behavior, and the record is corrected here:

| Behavior | Status | Client consequence |
|---|---|---|
| 10 req/s per project → raw `429`; 100 concurrent and 600 req/min per site to the content source; 500 pending jobs per topic | Documented | An explicit, testable rate limiter — not a sleep loop |
| `503` whose `x-error` header contains the literal substring `"(429)"` means the **content source** throttled, not the Admin API | Documented | The two MUST be distinguished and surfaced differently: the operator's remedy differs |
| A job `GET` returns **202** on success | Documented | Success is tested as **any 2xx**, never `=== 200` |
| A bulk index request with no body reindexes the **entire published site** | Documented | Gated (below); the client never sends an empty index body implicitly |
| Bulk writes silently ignore `/.helix/config` and `redirects.json` | Documented | The client reports which submitted paths were ignored |
| Publish and unpublish already purge the CDN | Documented | `cache purge` is a separate, rarer, CLI-only operation |
| `code` endpoints are keyed by GitHub owner/repo, not org/site | Documented | Distinct address shape in the client's types |
| Snapshots are pinned to `main` | Documented | No `ref` parameter on snapshot paths |
| PUT creates and returns `409` when the site already exists | **Inferred only** | **Do a GET before the write.** Never treat a caught `409` as the sole existence check |
| An empty-body snapshot POST means "add everything" | **Inferred only** | Always send an explicit JSON body with a content type; a synthetic test asserts the client never emits an empty-bodied snapshot POST |

### MCP tool surface: few, thick, task-shaped

One tool per subcommand is explicitly rejected — it mirrors `--help`, burns context on every request and saves the agent no orchestration. Nine tools, each described by **when to use it**:

| Tool | Shape | `readOnly` / `destructive` / `idempotent` |
|---|---|---|
| `eds_get_status` | `{ site, path, ref? }` — the single-path hot path, smallest possible call | `true / false / true` |
| `eds_get_status_bulk` | `{ site, ref?, paths[], select? }` — a POST that queries, not mutates | `true / false / true` |
| `eds_set_live_state` | `{ site, ref?, paths[], state: "published"\|"unpublished", wait? }` — chains job polling internally | `false / true / true` |
| `eds_get_site_config` | `{ site }` — aggregates site doc + CDN + effective config, since the site doc alone does not resolve inheritance | `true / false / true` |
| `eds_reindex` | discriminated union (see gate below) | `false / false / true` |
| `eds_get_audit_log` | `{ site, ref?, since?, nextToken? }` — cursor passthrough | `true / false / true` |
| `eds_get_snapshots` | `{ site, id? }` — read half of the snapshot state machine | `true / false / true` |
| `eds_manage_snapshot` | `{ site, id, verb, paths?, reviewAction?, message? }` — mutating half, split from the read half because annotations are static per tool | `false / true / false` |
| `eds_get_job_status` | `{ site, ref?, topic, name }` — success is any 2xx | `true / false / true` |

**CLI-only, with reasons**: `site apply` / `site delete` / `site source set` (org-structural; needs local site-model context an MCP call has no business carrying); `key create` / `key delete` / `auth mint` (credential minting and rotation, high blast radius); `code show` / `sync` / `delete` (GitHub owner/repo-keyed and deploy-adjacent — easy for an agent to target the wrong repository); `version restore` (destructive config overwrite, rare); `cache purge` (redundant with publish/unpublish, rare); `robots show` / `sitemap rebuild` (low value for v1).

**Two hazards get shapes, not flags.** A boolean flag is easy to pass by accident; an unreachable branch is not.

1. **Full-site reindex** — `eds_reindex` takes a discriminated union: `{ site, ref?, scope: "paths", paths: string[] }` or `{ site, ref?, scope: "full-site", confirmFullReindex: true }`. The full-site branch is unreachable without both the literal discriminant and the literal-`true` field, mirroring the CLI's `--all --yes` double gate.
2. **Any bulk write** — `paths` is a non-empty array in the schema. An omitted or empty array is a schema rejection, never a silent "everything", which is exactly the documented empty-body trap.

### Conformance: amend the shared suite, do not fake a tool

`describeConformance`'s "a tool that shells out keeps stdout pure JSON-RPC despite the child inheriting fd 1" test defaults to a `read-echo`-shaped tool built on `runAllowlisted`. EDS has no such tool and must not grow a decorative one to satisfy a harness. `mcp-testing` therefore gains a domain-independent fd-1 contamination probe it owns itself, and `shellOutProbe` becomes optional.

**This must not weaken what the suite catches for packages that do shell out.** `magento-cloud` (change 4) will have `execFile`-based tools; when a package supplies `shellOutProbe`, the existing assertion runs exactly as it does today, unchanged. The new probe is additive coverage for the non-exec case, not a replacement.

### Cold-start budget: measured here, not guessed

The number is an **output of `sdd-apply`, not an input to this proposal**. The methodology is what this change locks:

1. Build the real `hiberus-eds-mcp` bundle.
2. Spawn `dist/server.js` cold (no warm pool) N ≈ 15–20 times, timing from `spawn()` to the `initialize` response the suite's `beforeAll` already performs.
3. Compute p50/p95 locally as a sanity check only.
4. Set the CI-blocking threshold from **real CI-runner** p95 with a documented safety margin (roughly p95 × 1.5–2, rounded to a clean number) — never from the local dev-machine figure, which is faster and more consistent than a shared runner.
5. Record the threshold **and the methodology that produced it** in the `mcp-conformance` spec, so the next person can re-derive it rather than inherit a magic number. Re-measure if the bundle's shape changes materially.

### Testing: synthetic-fixture-first

Zero recording of real API traffic. The audited source material contains real customer identifiers, this repository is public, and credential scrubbing does not solve business-data scrubbing. Fixtures are schema-accurate, derived from the documented response shapes, and use synthetic organization, site and domain names throughout. A hand-rolled fetch double (no new devDependency needed) covers: header shape, pacing against the documented rate, `429`-vs-`503`+`x-error` branching, the 202 job path, GET-before-write, tolerant site-list shapes (bare array and `{ sites: [...] }`), and `nextToken` pagination. Strict TDD: every behavior above starts as a failing test.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| **Auth bootstrap depends on a step outside this package** — the first `admin`-scoped key can only come from Adobe's own UI | High (certain, by design) | Documentation risk, not a code risk. `MissingCredentialError`'s remedy and the onboarding doc name the exact out-of-band step. The CLI must never fail opaquely on a missing first key. |
| **A minted key's value is returned exactly once and is never retrievable** — losing it means minting another | High | `auth mint` prints the value prominently and alone, states explicitly that it cannot be recovered, and tells the operator to store it before continuing. Covered by a test asserting the warning is emitted. |
| **Two inferred-only API behaviors** (PUT→409 on existing; empty snapshot POST body = "add everything") | Medium | Do not depend on either. GET before write; always send an explicit JSON body. Synthetic tests assert the client's behavior, never the live trap. |
| **Real customer identifiers exist throughout the audited Python source** and this repository is public | High | No Python source is copied. Every fixture, test, doc and example uses synthetic organization, site and domain names. CI secret scanning already blocks. |
| **Amending `mcp-conformance` touches a capability other packages depend on** — weakening it would silently reduce coverage for `magento-cloud` | Medium | The change is strictly additive: when `shellOutProbe` is supplied the existing assertion runs unchanged. A test proves the exec-based path still fails on a contaminating child. |
| **Cold-start threshold set too tight** and flakes CI on a slow runner | Medium | Threshold derives from CI-runner p95 with a documented margin, not the local figure; the methodology is recorded next to the number so it can be re-derived rather than nudged. |
| **First npm publish of `@hiberus-magento/eds` is manual** and cannot use trusted publishing | Medium | `docs/release-setup.md` already records this; the first publish is a deliberate, human, one-time step and is the last thing this change does. |

## Rollback Plan

All work lands on a branch. Until publish, rollback is abandoning the branch: `packages/eds` is new and nothing depends on it.

The two shared touchpoints need care:

- **`mcp-testing`** — the conformance amendment is additive and behind an optional option, so reverting that single commit restores the previous suite exactly, with no other package affected.
- **`servers.json` / `README.md`** — revert the entry and re-run the generator. The README is never hand-edited, so it cannot drift.

**If a real npm publish has already happened**, rollback is *not* unpublish-and-republish: npm never allows reusing a version number, and the unpublish window is narrow. Instead, `npm deprecate` the bad version with a message pointing at the fix and ship a patch. Publishing is therefore sequenced last, after every gate is green, precisely so this branch is rarely taken.
