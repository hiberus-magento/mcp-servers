## Exploration: eds-package (change 2 of 5) — EDS CLI + MCP server on top of mcp-servers-bootstrap

SECURITY NOTE: the Python source audited (`tools/eds-cli/eds.py`, outside this repo) contains real customer org/site/domain identifiers and one magento-cloud project id. NONE are reproduced below or anywhere in this artifact — every example uses synthetic names (`example-org`, `example-site`, `example.test`, etc). Only shapes/mechanisms are recorded.

### 1. EDS Admin API — verified in depth against official docs

Sources fetched directly this session: https://www.aem.live/docs/admin.html, https://www.aem.live/docs/admin-apikeys, https://www.aem.live/docs/limits (plus a web search cross-check).

**Auth** (VERIFIED, admin-apikeys): static API key, header `X-Auth-Token: <key>` OR `Authorization: token <key>`. Created via `POST /config/{org}/sites/{site}/apiKeys.json` with body `{ "description": "...", "roles": [...] }`; roles seen: `author`, `publish`, `develop`, `admin` (`admin` required to create/update/delete keys) — the Python CLI's fuller role list (`basic_author`, `basic_publish`, `config`, `config_admin`) is plausible but not directly confirmed in the fetched page; treat those extra names as INFERRED from the CLI until independently checked. Value returned once in the creation response ("will not be retrievable again"), default expiry ~1 year (12-month example in docs). List/update/delete endpoints exist; list returns metadata only, never the value.

**Rate limits — VERIFIES the prior exploration's "undocumented" claim WRONG; it is documented.** `docs/limits` states explicitly: admin API is rate limited to **10 requests/second per project**, throttled admin-API requests get a raw **429**. Content-source throttling is returned as **503 with an `x-error` header containing the literal substring `(429)` followed by the backend's message** — this is the exact mechanism the Python CLI greps for, and it IS official documented behavior, not reverse-engineered folklore. Additionally documented: **100 concurrent requests and 600 requests/minute per site** to the content source, and **max 500 pending jobs per topic**. Correction to record: the prior exploration's "single most valuable undocumented finding" claim should be walked back — it is real, just findable in `/docs/limits` rather than `/docs/admin.html`.

**Job polling** (VERIFIED): `GET /job/{org}/{site}/{ref}/{topic}/{jobName}` documents its own success code as **202**, not 200 — confirms "success = any 2xx" is required, not a CLI workaround for a bug.

**PUT/POST semantics** (PARTIALLY VERIFIED): docs literally label the two operations "Create Site Config" (PUT) and "Update Site Config" (POST) — confirms create-vs-update. The **409-on-existing-PUT** behavior itself is NOT stated verbatim in the fetched text — that specific status code is INFERRED from the Python CLI's practical behavior (it always GETs first specifically to avoid relying on this). Design recommendation: keep the GET-before-write pattern rather than trusting an unconfirmed 409 contract.

**Other traps — all VERIFIED against docs, not just inferred**:
- Bulk index with empty body reindexes everything published: docs literally say "If no payload is given, it re-indexes every resource that is published."
- Bulk preview/publish "always ignore" `/.helix/config` and `redirects.json` — stated in docs for both operations verbatim.
- Publish/unpublish already purge "the live cdn and the byo cdn, if configured" — separate `cache purge` endpoint exists for out-of-band purges.
- Code endpoints are `/code/{owner}/{repo}/{ref}/{path}` — GitHub-keyed, confirmed distinct from the `{org}/{site}` shape everything else uses.
- Snapshots are hardcoded under `/main/` in every snapshot path — confirmed, no ref parameter exists for snapshots.
- The "empty POST body + no content-type = add everything" snapshot trap is NOT independently re-verified this session (not surfaced by the fetched pages); status stays INFERRED-from-CLI, carried over from the prior exploration, and should be an explicit synthetic-fixture test case rather than an assumption baked silently into the client.

### 2. Python `eds.py` re-read for implementation — full 1503-line file read

**Genuinely valuable day-to-day commands** (justify the MCP tool set below): `status show`, `preview/live show|publish|unpublish|bulk`, `site show|list`, `index show|update|bulk`, `log tail`, `job show|wait`, `snapshot list|show|add|remove|publish|review|delete`, `robots show`, `sitemap rebuild`, `version list`, `config effective`.

**Vestigial / out of domain for an EDS MCP+CLI package** (do not port): `spec build`, `dns list|check`, `config from-file` (shells to `php`), `config from-db` (shells to `magento-cloud db:sql`) — these are customer-project-specific spec-generation/DNS bookkeeping tools coupled to a bespoke 32-site vertical model and a separate Commerce CLI; porting them would smuggle unrelated domain logic and an unrelated `execFile` allowlist entry (`php`, `magento-cloud`) into a generic `hiberus-eds` package. Recommend treating the "spec/catalog-views hand-off" pattern (already documented in the mcp-conformance spec's shared synthetic fixture) as the only reusable idea, not the code.

**Response-shape knowledge a TS client must reproduce**: job envelope `{ job: { topic, name, state, progress: { total, processed, failed } }, links: { self } }`, never construct the self URL manually (topic on the URL doesn't match the response topic for some bulk ops per the CLI's own comment); log entries `{ entries: [...], nextToken }`; site list responses are sometimes a bare array and sometimes `{ sites: [...] }` — client must accept both; `_show()`'s per-partition summarization (`edit/preview/live/code/index` sub-objects with `status/lastModified/permissions/url`) is worth keeping as an internal formatting convenience, not the wire contract.

**Error handling to carry over**: no retries/refresh (correct for a static, non-expiring-in-practice key); every non-2xx surfaces `HTTP {status}: {body}`; specific 401/403/404 hints per resource. **What to improve**: the Python client's homegrown pacing (`MIN_GAP=0.12s`) should become an explicit, testable rate limiter in `mcp-core` or a small eds-local helper — not a "spinlock" `time.sleep` loop; the TS version should also branch 429 vs 503+`x-error~=(429)` and surface which side is throttling, exactly matching the now-verified official semantics.

**Confirmed DROP, with the security constraint as added justification, not just the "no MCP equivalent" argument**:
- macOS Keychain fallback via the `security` binary — forbidden per workspace policy (no native keychain dependency) and would require an `execFile` allowlist entry (`security`) that has no cross-platform equivalent; mcp-core's `resolveCredentialValue` (env → `$XDG_CONFIG_HOME/hiberus/<domain>.json`) already fully replaces it.
- The browser-console JS generator (`site browser`) — recommend dropping entirely, not just "no MCP tool for it." It duplicates a session-cookie-based auth path the MCP transport spec explicitly steers stdio implementations away from, and it writes an executable payload to disk for the operator to paste into devtools — a real security smell inconsistent with the workspace's posture. If a genuinely keyless bootstrap path is needed, it should be "get a key from the AEM Sidekick UI," not a generated script.

### 3. Auth design, concretely

`mcp-core`'s `StaticTokenProvider` + `resolveCredentialValue`/`persistCredential` in `packages/mcp-core/src/credentials/{token-provider,resolve}.ts` already implement EDS's exact needs with **zero code changes required**: env var (`EDS_TOKEN`) over `$XDG_CONFIG_HOME/hiberus/eds.json` (mode 0600) over `MissingCredentialError` with an actionable remedy message (`cliCommand`, `envVar`, `configPath`, `reason`) — this is a direct, unmodified reuse, not an extension point. `MintedTokenProvider` (expiry-aware, single-flight, generation-stamped) is available but **not needed for the primary session token** — EDS keys are static with a ~1-year expiry, not short-lived/auto-refreshed. It could, however, back a distinct "mint a fresh scoped key" CLI-only operation if that operation itself needs its own request coalescing — low priority, not required for v1.

**Should `hiberus-eds` mint a key or only accept a pasted one? Both, sequenced.** The bootstrap chicken-and-egg is real: minting via `POST .../apiKeys.json` requires an EXISTING credential with the `admin` role, and there is no way to get that first credential from our own tooling — Adobe's own UI/Sidekick is the only source of a brand-new organization's very first key. Day-one flow: (1) human obtains an initial `admin`-scoped key from the AEM Sidekick/admin UI (out of this package's control); (2) pastes it via `echo "$KEY" | hiberus-eds auth token set` (stdin only, matches mcp-core's CLI contract — no `--token` flag exists anywhere); (3) once an admin-scoped key is active, a CLI-only `hiberus-eds auth mint --scope <org|site> --roles <...>` command can call the documented endpoint to mint additional, narrower-scoped keys for day-to-day/automation use, rather than reusing the powerful bootstrap key everywhere. `auth mint` stays CLI-only (org-structural, high blast radius, matches the already-decided exclusion of `key create`/`key delete` from the MCP tool surface).

**`auth status` without leaking the key**: mirror the Python CLI's approach of probing 2–3 cheap read endpoints (e.g. `GET /config/{org}.json`, `GET /config/{org}/sites.json`, a profile-equivalent call) and reporting `200/401/403/404` per probe with a plain-English verdict, never echoing the key value; redaction (`packages/mcp-core/src/redact/redact.ts`) already masks `authorization`/`token` key-value pairs in any log line, as defense in depth.

**Missing/expired credential surfaced to an agent**: `defineTool`'s `invoke()` already catches `MissingCredentialError`/`CredentialExpiredError` and returns `{ content: [...], isError: true }` with the formatted remedy text (`Missing credential for domain "eds".\nRun: hiberus-eds auth token set (reads the token from stdin)\nOr set: EDS_TOKEN=<value>\nChecked: <path> (not found)`) — this is already the exact actionable text an agent would relay; no new mechanism needed, just wiring EDS's `Remedy` object correctly.

### 4. MCP tool design (grounded, ~7-8 tools)

Key architectural finding: **EDS needs none of `mcp-core`'s exec/allowlist primitives.** It is a pure HTTPS/fetch client — no local binary is ever shelled out for its own domain logic. This is the first domain package that exercises credentials + redaction + truncation/pagination + `defineTool` without touching `run-allowlisted`/`CommandAllowlist` at all — see Risk #2 below for why that is not entirely friction-free against the current conformance suite.

Proposed tools (annotations chosen per `ToolAnnotations`'s enforced pairing):
1. **`eds_get_status`** — `{ site, path, ref? }`, wraps single-path `status show`; `readOnlyHint:true`.
2. **`eds_get_status_bulk`** — `{ site, ref?, paths: string[], select?: ("edit"|"preview"|"live")[] }`, wraps `status bulk` (a POST that queries, doesn't mutate); `readOnlyHint:true`. Kept separate from #1 rather than folded in, so the single-item hot path stays the smallest possible call shape.
3. **`eds_set_live_state`** — `{ site, ref?, paths: string[], state: "published"|"unpublished", wait?: boolean }`, wraps `live publish`/`unpublish` (single or array), chains job-wait polling internally when `wait` is set, treats any 2xx (incl. 202) as accepted; `readOnlyHint:false, destructiveHint:true, idempotentHint:true` (re-publishing/re-unpublishing the same paths converges to the same state).
4. **`eds_get_site_config`** — `{ site }`, wraps `site show` + `cdn show` + `config effective` (aggregated) in one call, since the site doc alone doesn't resolve profile inheritance; `readOnlyHint:true`.
5. **`eds_reindex`** — discriminated union input: `{ site, ref?, scope: "paths", paths: string[] } | { site, ref?, scope: "full-site", confirmFullReindex: true }` — the full-site branch is unreachable without the extra literal-`true` field, mirroring the CLI's `--all --yes` double gate so a full reindex can never be triggered by a loosely-typed agent call; `readOnlyHint:false, destructiveHint:false, idempotentHint:true`.
6. **`eds_get_audit_log`** — `{ site, ref?, since?, nextToken? }`, wraps `log tail`, cursor pagination passthrough; `readOnlyHint:true`.
7. **`eds_get_snapshots`** — `{ site, id? }`, wraps `snapshot list`/`show` (read-only half only); `readOnlyHint:true`.
8. **`eds_manage_snapshot`** — `{ site, id, verb: "add"|"remove"|"publish"|"review"|"delete", paths?, reviewAction?, message? }`, wraps the mutating half of the snapshot state machine as one tool with a verb enum (always on `main`); `readOnlyHint:false, destructiveHint:true, idempotentHint:false` — deliberately split from #7 because `defineTool`'s annotations are static per tool and a single tool spanning both read and destructive verbs would force over-annotating the read paths as destructive.
9. **`eds_get_job_status`** — `{ site, ref?, topic, name }`, wraps `job show`/`wait`, success = any 2xx; `readOnlyHint:true, idempotentHint:true`.

**Explicitly CLI-only, with reasons**: `site apply`/`site delete`/`site source set` (org-structural, creates/deletes/rewires sites, needs local site-model context an MCP call has no business carrying); `key create`/`key delete`/the new `auth mint` (credential minting/rotation, high blast radius); `code show`/`sync`/`delete` (GitHub-owner/repo-keyed, deploy-adjacent, easy foot-gun for an agent to target the wrong repo); `version restore` (destructive org/site config overwrite, rare); `cache purge` (rare given publish/unpublish already purge; add later only if real usage demands it); `robots show`/`sitemap rebuild` (low value, keep CLI-only for v1, revisit if requested); `spec build`/`dns *`/`config from-file`/`config from-db`/`site browser` (out of domain entirely per section 2, not ported to either surface).

### 5. Testing strategy

**Endorse and strengthen the prior exploration's synthetic-fixture recommendation.** Having now verified the API in depth against three official pages (auth, endpoint reference, limits), the response shapes and error semantics are documented precisely enough — including the exact `503` + `x-error` "«(429)»" mechanism — that schema-accurate synthetic fixtures can be built with high confidence, without recording against any real or sandbox tenant. Recommend **zero real API recording for `eds-package` v1**; revisit only if a sandbox tenant becomes available later and a specific behavior still can't be pinned down from docs (the one remaining candidate is the "empty snapshot POST body = add everything" trap, which is INFERRED-only — worth one explicit synthetic test asserting the client always sends a JSON body with a real content-type, never testing the live trap itself).

**Strict TDD (`pnpm test`) coverage plan**: a hand-rolled fetch double (consistent with the package's zero-runtime-dependency ethos — an external mocking library would be a devDependency and wouldn't violate the packaging gate, but isn't necessary here) covering: header shape (`X-Auth-Token` vs `Authorization: token`), rate-limit pacing (≥ the documented 10 req/s, verified via fake timers), 429-vs-503+"(429)" branching, job-envelope parsing incl. the 202 success path, PUT-then-409-if-exists via GET-before-write (not by trusting an unconfirmed status code), and pagination via `nextToken`. The shared `mcp-conformance` suite (`describeConformance`) runs unmodified against the built `hiberus-eds` bundle for tool metadata completeness, stdout purity, and the packaging gate.

**Cold-start timing — this change owns fixing it.** Concrete measurement plan: (1) build the real `hiberus-eds` bundle; (2) spawn `dist/server.js` cold (no warm pool) N≈15–20 times, measuring wall-clock from `spawn()` to the `initialize` response the existing `describeConformance` `beforeAll` already performs; (3) compute p50/p95 locally first as a sanity check; (4) set the CI-blocking threshold from actual CI-runner timing (not the local dev-machine number, which is typically faster/more consistent than shared CI runners) with a documented safety margin (e.g. p95 × 1.5–2, rounded to a clean number), recorded as a new `mcp-conformance` requirement/scenario ("Cold-Start Time Budget") together with the measurement methodology in a comment, not an invented round number. Plan to re-measure if the bundle's shape changes materially later (e.g. a future package adds heavier dependencies).

### 6. Risks and open questions

1. **Cold-start threshold number is not yet known** — by design, it can only be set after real measurement during `sdd-apply` of this change; propose should lock the *methodology* (above), not a number.
2. **Conformance suite's shell-out probe assumes an execFile-based tool per package; EDS has none.** `describeConformance`'s "keeps stdout pure JSON-RPC despite the child inheriting fd 1" test and its `readOnlyIntrospections` checks default to a `read-echo`-shaped tool that shells out via `runAllowlisted`. EDS's real tools are pure HTTP and never touch `mcp-core`'s executor. Needs a decision in `sdd-propose`/`sdd-design`: (a) keep the template's harmless `noop`/`read-echo` tools shipped alongside the real EDS tools purely as conformance scaffolding, or (b) amend `mcp-conformance` so `describeConformance` owns its own generic child-process probe independent of any domain tool. Option (b) is architecturally cleaner and avoids every future non-exec domain package (ACO likely has the same shape) carrying dead scaffolding tools forever, but it is a change to an already-merged, CI-blocking spec and should be scoped deliberately rather than folded in silently.
3. **Auth bootstrap depends on a step outside this package's control** (obtaining the very first `admin`-scoped key from Adobe's own UI) — must be documented clearly in onboarding; not a code risk, but a UX/documentation one.
4. **PUT-409-on-existing is inferred, not doc-verified** — mitigated by design (GET-before-write), but worth a synthetic test asserting the client never relies on catching 409 as its sole existence check.
5. **`EDS_AUTH_HEADER` custom-header override** (Python CLI supports an arbitrary header name via env var) could not be corroborated as a generic AEM requirement from the fetched docs — recommend treating it as vestigial/project-specific and dropping it from the TS client unless a concrete counter-example surfaces later.
6. **Real customer identifiers** live throughout `eds.py`'s constants; this exploration and all downstream artifacts must keep using synthetic org/site/domain names exclusively (the repo's public history has already needed two rewrites for this).
7. **Full Python role list** (`basic_author`, `basic_publish`, `config`, `config_admin`) is CLI-only-observed, not independently doc-confirmed this session — treat as tentative until spot-checked, e.g. via a real `key list` response shape if a sandbox ever becomes available.

### Ready for Proposal

Yes. Auth design, tool surface, and testing strategy are concrete enough to propose directly. Flag risk #2 (conformance shell-out-probe assumption) and the cold-start measurement methodology (not a number) as explicit decisions for `sdd-propose` to lock, alongside confirming the CLI-only exclusion list in section 4.

## Key Learnings

1. Adobe's official `/docs/limits` page documents the 429-vs-503-with-x-error-"(429)" disambiguation verbatim; the prior exploration's "undocumented, reverse-engineered" characterization was incorrect and should be corrected in the proposal.
2. `mcp-core`'s `StaticTokenProvider` and `resolveCredentialValue` already fully satisfy EDS's static-key auth model with zero code changes — EDS is a pure consumer, not an extension point.
3. EDS is a pure HTTPS/fetch domain with no local binary shelling, which exposes a real gap: the shared conformance suite's stdout-purity probe currently assumes every package has an execFile-based tool to test against.
4. The EDS Admin API's auth bootstrap has an inherent chicken-and-egg dependency on Adobe's own UI to mint the very first admin-scoped key; `hiberus-eds` must support both paste-a-key and mint-a-key flows, sequenced.
5. Several "undocumented traps" from the prior exploration (bulk index full reindex, bulk write ignoring config files, code endpoints keyed by owner/repo, snapshots pinned to main) are in fact stated verbatim in `docs/admin.html`, while PUT-409-on-existing and the empty-snapshot-body trap remain genuinely inferred from the CLI only.
